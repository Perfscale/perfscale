# Справочник по YAML

Нативный запуск управляется двумя файлами: **определение теста** (`-f`)
описывает, *что* делать; **конфиг** (`-c`) описывает, *сколько нагрузки*
подавать.

Оба файла валидируются по JSON Schema до выполнения — ошибки указывают на
путь конкретного поля, а не на сырой вывод парсера. Схемы лежат в
[`schema/`](../schema/) и могут включать автодополнение в редакторе через
модлайн:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/Perfscale/perfscale/main/schema/test.schema.json
```

## Определение теста (`-f test.yaml`)

Один массив `steps`. Каждый виртуальный пользователь (VU) выполняет весь
список в цикле, пока не истечёт заданная длительность. Опциональный
верхнеуровневый `import:` наследует базовый документ — см.
[Композиция документов](#composing-documents-import). Опциональный
верхнеуровневый `libraries:` объявляет библиотеки генераторов значений для
токенов `${alias.fn(...)}` — см. [Библиотеки](#libraries-libraries).

```yaml
steps:
  - name: login                     # необязательная метка для вывода в лог
    use: std/http@v1                # обязательно — идентификатор действия
    with:                           # параметры действия (см. ниже)
      method: POST
      url: https://api.example.com/login
      body:
        user: demo
    check:                          # необязательные инлайн-проверки
      status: 200
      duration_ms_lt: 500
    outputs: login                  # необязательно — сохранить вывод для следующих шагов
```

### Поля шага

| Поле | Обязательно | Описание |
|---|---|---|
| `use` | да | Идентификатор действия: `std/http@v1`, `std/graphql@v1`, `std/tcp@v1`, `std/udp@v1`, `std/pubsub@v1`, `std/llm@v1`, `std/ws@v1`, `std/ws-connect@v1`, `std/ws-send@v1`, `std/ws-recv@v1`, `std/ws-ping@v1`, `std/ws-close@v1`, `std/grpc@v1`, `std/grpc-connect@v1`, `std/grpc-call@v1`, `std/grpc-stream-open@v1`, `std/grpc-stream-send@v1`, `std/grpc-stream-recv@v1`, `std/grpc-stream-close@v1`, `std/db-connect@v1`, `std/db-query@v1`, `std/db-tx-begin@v1`, `std/db-tx-commit@v1`, `std/db-tx-rollback@v1`, `std/db-close@v1`, `std/check@v1`, `std/sleep@v1`, `std/log@v1`, `std/file-read@v1`, `std/file-write@v1`, `std/child_process@v1`, `std/kill_process@v1`, `std/thresholds@v1`, `std/set_shared_variable@v1`, `std/get_shared_variable@v1` (также работают короткие алиасы `http`, `graphql`, `tcp`, `udp`, `pubsub`, `llm`, `ws`, `ws-connect`, `ws-send`, `ws-recv`, `ws-ping`, `ws-close`, `grpc`, `grpc-connect`, `grpc-call`, `grpc-stream-open`, `grpc-stream-send`, `grpc-stream-recv`, `grpc-stream-close`, `db-connect`, `db-query`, `db-tx-begin`, `db-tx-commit`, `db-tx-rollback`, `db-close`, `check`, `sleep`, `log`, `file-read`, `file-write`, `child_process`, `kill_process`, `thresholds`, `set_shared_variable`, `get_shared_variable`). `uses:` принимается как алиас для `use:` |
| `name` | нет | Человекочитаемая метка, отображаемая в строках лога |
| `with` | нет | Параметры действия — см. [Действия](core/actions.md) |
| `check` | нет | Проверки вывода этого шага — те же ключи, что у `std/check@v1` |
| `outputs` | нет | Имя переменной, под которой сохраняется вывод шага |
| `severity` | нет | Только для `std/thresholds@v1`: во что превращается нарушенный порог — `fail` (по умолчанию; запуск завершается с ненулевым кодом), `warn` или `info` |
| `message` | нет | Только для `std/thresholds@v1`: пользовательская метка, добавляемая к сводке нарушений (интерполируется) |

### Переменные (`${{ ... }}`)

Шаги передают данные последующим шагам через плейсхолдеры в стиле GitHub
Actions. Шаг сохраняет свой вывод под именем, заданным в `outputs:`; любое
**строковое значение** в `with:` или `check:` последующего шага может затем
ссылаться на него:

| Выражение | Раскрывается в |
|---|---|
| `${{ name }}` | Весь сохранённый вывод, приведённый к строке |
| `${{ name.field }}` | Одно поле сохранённого объекта (например, `.status`, `.body`, `.duration_ms`) |
| `${{ name.a.b }}` | Вложенный путь — один уровень JSON на каждую `.`, например `${{ resp.headers.x-request-id }}` |
| `${{ __last__ }}` / `${{ __last__.field }}` | Вывод непосредственно предыдущего шага — всегда доступен, `outputs:` не нужен |
| `${{ config.<name>.<field> }}` | Вывод шага инициализации `before:` из конфиг-файла (см. [Конфиг](#config--c-configyaml)) |
| `${{ vars.<key> }}` | Статическое значение из блока `variables:` конфиг-файла |
| `${{ env.NAME }}` | Переменная окружения процесса `NAME` — для секретов (`api_key`, токенов, DSN), которые не должны храниться в YAML |

Для `std/http@v1` сохранённый вывод имеет вид
`{ "status": <int>, "body": <string>, "duration_ms": <float>, "headers": <object> }`
— имена заголовков приводятся к нижнему регистру, поэтому заголовок сессии
или токена из ответа 1 может перейти в запрос 2:

```yaml
steps:
  - use: std/http@v1
    with: { url: "https://api.example.com/first" }
    outputs: r1
  - use: std/http@v1
    with:
      url: "https://api.example.com/second"
      headers:
        x-session: "${{ r1.headers.x-session }}"
```

```yaml
steps:
  - name: login
    use: std/http@v1
    with:
      method: POST
      url: "https://api.example.com/token"
      body: { user: demo }
    outputs: auth                          # ← сохраняется как `auth`

  - name: fetch profile
    use: std/http@v1
    with:
      url: "https://api.example.com/me"
      headers:
        authorization: "Bearer ${{ auth.body }}"   # вложенные значения работают
    check:
      body_contains: "${{ auth.body }}"            # и в check тоже

  - use: std/log@v1
    with:
      message: "login took ${{ auth.duration_ms }}ms → ${{ auth.status }}"
```

Правила и граничные случаи:

- Плейсхолдеры работают в строковых значениях на **любой глубине**
  `with`/`check` — во вложенных объектах (заголовки), элементах массивов,
  телах запросов. Ключи никогда не интерполируются.
- Пробелы внутри фигурных скобок игнорируются: `${{auth.status}}` ≡
  `${{ auth.status }}`.
- **Отсутствующая переменная или поле раскрываются в пустую строку** —
  запуск не падает. Проверяйте значение через `check:`, если отсутствие
  должно быть ошибкой. **Исключение:** `${{ env.NAME }}` с неустановленным
  `NAME` **проваливает шаг** с ошибкой `env var 'NAME' is not set` до запуска
  действия — иначе молча пустой `api_key` проявился бы как непонятный 401 от
  API.
- `${{ env.NAME }}` читает окружение процесса `perfscale` (всё после `env.` —
  это имя переменной). `env` — зарезервированный префикс: сохранённый вывод с
  именем `env` будет им перекрыт. Раскрытые значения подставляются только в
  параметры шагов — движок сам никогда не пишет их в логи или сводки. Он
  также записывает каждое раскрытое значение `env.*` в реестр уровня запуска
  и **маскирует его в логе запуска**: значения длиной 4+ символа заменяются
  на `***` везде, где встречаются (в том числе внутри URL и DSN), более
  короткие — только как целые токены, — так что секрет, случайно попавший в
  URL запроса или сообщение `std/log@v1`, всё равно не утечёт в вывод. Именно
  поэтому `env.*` — правильный канал для секретов.
- Сегменты пути спускаются на один уровень JSON-объекта за каждую `.` —
  заголовки с точками в имени адресовать нельзя (редкий случай; всё остальное
  работает).
- Плейсхолдеры раскрываются отдельно для каждого виртуального пользователя и
  каждой итерации — каждый VU видит выводы только своей цепочки шагов,
  никогда чужой.
- Шаги без `${{` выполняются как есть: движок полностью пропускает проход
  интерполяции, поэтому обычные шаги не платят за эту возможность ничем.
- Кавычки в YAML: работают и без кавычек (`Bearer ${{ auth.body }}`), и в
  кавычках (`"${{ auth.body }}"`); ставьте кавычки, если значение начинается с
  символа, который YAML трактует специально (`{`, `[`, `*`, …).

## Конфиг (`-c config.yaml`)

```yaml
vus: 10          # виртуальные пользователи, по умолчанию 1
duration: 5m     # "30s", "500ms", "1.5s", "1m", "5m30s", "1h" — по умолчанию "1m"

report:          # необязательно — пересылка метрик в инстанс perfscale serve
  url: http://localhost:7999
  during_run: true      # также стримить накопительные снапшоты во время работы

gpu:             # необязательно — метрики GPU во время запуска (нативный движок)
  enabled: true
  interval_ms: 1000
  source: nvidia-smi
```

| Поле | По умолчанию | Описание |
|---|---|---|
| `vus` | `1` | Одновременные виртуальные пользователи (фиксированный профиль) |
| `duration` | `1m` | Длительность запуска по реальному времени; голые числа — секунды; доли секунды (`"500ms"`, `"1.5s"`) поддерживаются нативным движком |
| `stages` | — | Профиль ramping-VU (в стиле k6): список стадий `{ duration, target }`. Переопределяет `vus`/`duration`; взаимоисключающий с `arrival`. Только нативный движок |
| `arrival` | — | Профиль arrival-rate (открытая модель): `{ max_vus, pre_allocated_vus?, stages: [{ duration, rate }] }` — поддержание заданной частоты итераций/с. Взаимоисключающий со `stages`. Только нативный движок |
| `report.url` | — | Базовый URL инстанса `perfscale serve`; флаг CLI `--report` переопределяет его |
| `report.during_run` | `false` | Также стримить накопительные снапшоты метрик во время запуска (батчевые POST на `<url>/api/v1/metrics`), а не только сводку в конце — см. [Метрики во время запуска](core/metrics.md#during-run-metrics-reportduring_run). Только нативный движок |
| `report.interval_ms` | `5000` | Интервал снапшотов/сброса во время запуска, миллисекунды (мин. 1000) |
| `report.batch_size` | `500` | Сбрасывать батч, как только в нём накопится столько сэмплов |
| `report.max_cpu_percent` | `90` | Порог по CPU: пока загрузка CPU хоста ≥ этого значения, батчи удерживаются (без POST), а снапшоты ставятся в очередь — никогда не теряются — пока порог не откроется; `0` отключает; вне Linux не действует |
| `report.max_pending` | `24` | Мягкий лимит недоставленных батчей — при превышении выводится предупреждение, но батчи сохраняются и доставляются по порядку, никогда не теряются посреди запуска |
| `gpu` | — | Сбор метрик GPU — см. [Метрики GPU](#gpu-metrics-gpu). Только нативный движок |
| `before` | `[]` | Одноразовые шаги инициализации — см. [Инициализация и переменные](#setup-and-variables) |
| `after` | `[]` | Одноразовые шаги завершения — см. [Завершение](#teardown-after) |
| `variables` | `{}` | Статические значения, доступные шагам как `${{ vars.* }}`. Не храните секреты в этом блоке — это обычный YAML, попадающий в репозитории и диффы; для них используйте `${{ env.NAME }}` (окружение процесса, маскируется в логах запуска) |
| `shared_variables` | `{}` | Изменяемое общее состояние между VU для `std/set_shared_variable@v1` / `std/get_shared_variable@v1`: отображение имя → начальное JSON-значение (тип выводится из него). Объявление обязательно — шаг, ссылающийся на необъявленное имя, или `op`, несовместимая с объявленным типом, проваливает валидацию до старта запуска. См. [руководство по общим переменным](core/shared-variables.md). Только нативный движок |
| `allow_process_actions` | `false` | Разрешить шагам запускать/сигналить процессам ОС (`std/child_process@v1`, `std/kill_process@v1`). Fail-closed: список шагов из недоверенного источника не может трогать процессы, пока вы явно не разрешите |
| `allow_library_capabilities` | `false` | Разрешить записям `libraries:` нести непустые выдачи `capabilities:`. Fail-closed, тот же паттерн, что у `allow_file_actions` |
| `seed` | — | Seed детерминизма уровня запуска: каждый генератор `${…}` и экземпляр библиотеки выводит свой seed как `hash(seed, vu_id, conn_seq)`, поэтому запуск с seed воспроизводит те же сгенерированные значения. Реальное время остаётся недетерминированным |
| `libraries` | — | Библиотеки генераторов значений для токенов `${alias.fn(...)}` — см. [Библиотеки](#libraries-libraries) |
| `import` | — | Базовый документ для наследования — см. [Композиция документов](#composing-documents-import) |

### Метрики GPU (`gpu:`)

Сэмплирование GPU хоста (utilization, VRAM, температура, мощность) на
протяжении всего запуска с секцией `gpu` в сводке запуска — в первую очередь
чтобы коррелировать нагрузку [`std/llm@v1`](core/llm.md) с состоянием GPU.
По умолчанию выключено; сбои сбора (нет GPU, отсутствуют утилиты) пишут одно
предупреждение и никогда не проваливают запуск.

```yaml
gpu:
  enabled: true
  interval_ms: 1000                          # по умолчанию 1000 (мин. 10)
  source: nvidia-smi                         # nvidia-smi (по умолчанию) | dcgm
  dcgm_url: http://127.0.0.1:9400/metrics    # для source: dcgm
  devices: [0, 1]                            # необязательно; по умолчанию — все GPU
```

Полное руководство: [core/gpu.md](core/gpu.md).

### Профили нагрузки

Нативный движок поддерживает три профиля нагрузки. `stages`/`arrival`
переопределяют `vus`/`duration` (lint предупреждает, если задано и то, и
другое) и взаимоисключают друг друга; длительность запуска — сумма
длительностей стадий.

**Фиксированный** (по умолчанию): `vus` воркеров крутят шаги в цикле в
течение `duration`.

```yaml
vus: 10
duration: 5m
```

**Ramping VUs** (`stages:`, в стиле k6): целевое число VU линейно
интерполируется между целями стадий — первая стадия поднимается с 0, каждая
следующая — от `target` предыдущей стадии. Снижение происходит плавно: VU,
который убирается, завершает текущий шаг и выходит на следующей границе шага.

```yaml
stages:
  - { duration: 30s, target: 10 }  # рост 0→10 VU
  - { duration: 1m,  target: 50 }  # рост 10→50 VU
  - { duration: 30s, target: 0 }   # снижение до нуля
```

**Arrival-rate** (`arrival:`, открытая модель): движок поддерживает профиль
частоты итераций в секунду и масштабирует пул воркеров, чтобы успевать, —
новые итерации стартуют по расписанию, даже когда тестируемая система
замедляется (там, где цикл с фиксированным числом VU растянулся бы). `rate`
линейно растёт между стадиями (допустимы дроби: `0.5` = одна итерация каждые
2 с).

```yaml
arrival:
  max_vus: 100              # потолок пула воркеров — обязательно, ≥ 1
  pre_allocated_vus: 10     # воркеры, созданные заранее (по умолчанию 1); пул растёт лениво до max_vus
  stages:
    - { duration: 30s, rate: 5 }    # рост 0→5 итераций/с
    - { duration: 1m,  rate: 20 }   # рост 5→20 итераций/с
```

Разрешение, пришедшее, пока все `max_vus` воркеров заняты, отбрасывается и
учитывается в сводной метрике `dropped_iterations` (плюс предупреждение в
лог не чаще раза в 5 с) — увеличьте `max_vus` или снизьте частоту, если она
растёт.

Для запусков со `stages`/`arrival` строка `vus` в сводке показывает
наблюдаемый параллелизм (`vus....................: <last> min=<min> max=<max>`),
периодическая строка `[stats]` получает в конце поле `vus=N`, а экспорты
сводки (`--summary-export`) возвращают `vus: null` с `duration`, равным сумме
длительностей стадий.

Длительности стадий используют ту же грамматику `"500ms"`/`"30s"`/`"1m30s"`/`"1h"`,
что и `duration`, но валидируются строго: нечитаемая или нулевая длительность
стадии проваливает запуск (и `perfscale lint`) с понятной ошибкой. `stages` и
`arrival` доступны только в нативном движке — с `--locust` они отклоняются
(используйте `vus`/`duration`), с `--k6` конфиг-файл всё равно игнорируется.
См. [examples/ramping.config.yaml](../examples/ramping.config.yaml),
[examples/spike.config.yaml](../examples/spike.config.yaml) и
[examples/arrival-rate.config.yaml](../examples/arrival-rate.config.yaml).

### Библиотеки (`libraries:`)

Библиотеки предоставляют функции-генераторы значений для токенов `${...}`
(RFC 005) — настоящие UUID, ULID, данные в стиле faker, даты — помимо
встроенных `${seq}`/`${rand(a,b)}`/`${uuid}`/`${now}`. Объявляются в
конфиг-файле, файле теста или в обоих (объявления конкатенируются;
дублирующийся алиас — ошибка валидации):

```yaml
libraries:
  - use: '@std/random@v1'          # встроенная; алиас по умолчанию: random
    capabilities: []               # обязательный ключ — [] означает «без разрешений»
  - use: '@std/random@v1'
    as: ids                        # алиас → префикс токена ${ids.fn(...)}
    capabilities: []
  - use: ./libs/fixer-ids.wasm     # локальный WASM-компонент (путь относительно этого файла)
    capabilities: []
  - use: 'https://vendor.example.com/fixer-ids.wasm'   # удалённый: perfscale install
    sha256: '9f2c…64 hex…'
    capabilities: []
  - use: 'git+https://github.com/org/repo.git@v1.2.3#libs/fixer-ids.wasm'  # git: perfscale install
    capabilities: []
```

Полезные нагрузки в действиях, раскрывающих `${...}` (http, ws, gRPC,
GraphQL, tcp, udp, llm, параметры db, pubsub, file-write — всё, кроме
std/log), могут затем вызывать функции библиотеки:

```yaml
with:
  send: '{ "id": "${random.ulid()}", "who": "${random.email()}", "n": "${ids.int(1000,9999)}" }'
```

Правила:

- Встроенные токены (`${seq}`, `${rand}`, …) сопоставляются первыми и не
  изменяются. Алиас не может перекрывать их имена.
- Неизвестный алиас → токен остаётся как есть. Известный алиас + неизвестная
  функция (или неверные аргументы) → шаг **проваливается** — опечатка не
  должна молча попасть в полезную нагрузку.
- Аргументы отображаются текст → JSON по фиксированному контракту: разбиение
  по запятым вне двойных кавычек, обрезка пробелов, снятие одной пары
  окружающих кавычек, разбор как JSON при возможности, иначе — строка. Так
  `pick(a|b|c)` передаёт одну строку `"a|b|c"`, а `int(1,100)` — два числа.
- Опциональный завершающий аргумент `key` любой функции мемоизирует результат
  **в пределах одного сообщения**: `${random.uuid4(order)}`, встретившийся
  дважды в одном сообщении, даёт один id; следующее сообщение генерирует
  новый.
- `seed: 42` в конфиге делает запуск воспроизводимым: seed экземпляров
  выводятся как `hash(seed, vu_id, conn_seq)`.
- `capabilities:` **обязателен в каждой записи** — явный пустой список
  (`capabilities: []`) означает «без разрешений»; пропущенный ключ — ошибка
  валидации при загрузке, `lint` и запуске. Непустые разрешения (`fs`,
  `clock` или `{ net: [hosts] }`) требуют
  `allow_library_capabilities: true` (fail-closed, тот же паттерн, что у
  `allow_file_actions`). `@std/random@v1` не объявляет никаких capability —
  выдача ей любых — ошибка валидации. Библиотека, чей `info()` сообщает
  `"pure": true`, не нуждается в разрешениях для импортов `wasi:filesystem` /
  `wasi:clocks/wall-clock` (шум тулчейна jco) — и не получает preopen'ов,
  поэтому реальный доступ к файлам падает в рантайме.

#### Настройки запуска (`CallCtx.settings_json`)

Каждый вызов библиотеки получает настройки запуска как JSON-объект,
замороженный один раз при старте запуска, — строка идентична для каждого VU,
итерации и вызова в запуске:

```json
{
  "vus": 10,            // только фиксированный профиль, иначе null
  "duration_ms": 300000, // только фиксированный профиль, иначе null
  "seed": 42,           // seed из конфига или null
  "stages": null,       // профиль со стадиями: [{ "duration_ms", "target" }]
  "arrival": null,      // arrival-профиль: { "max_vus", "pre_allocated_vus", "stages": [{ "duration_ms", "rate" }] }
  "variables": {}       // `variables:` из конфига с раскрытыми ${{ env.* }}
}
```

`vus`/`duration_ms` задаются только для фиксированного профиля нагрузки;
запуски со стадиями и arrival-rate оставляют их null и несут профиль в
`stages`/`arrival` (длительности нормализованы до миллисекунд). `variables`
раскрываются через ту же интерполяцию, что используют шаги, — поэтому
значение из env, которое теперь получает библиотека, также записывается в
реестр секретов запуска и остаётся замаскированным в логе. Компоненты,
собранные под ABI WIT 0.1, получают `"{}"` (в контексте 0.1 нет поля
настроек).

#### Правила политики: `secret` / `allow` / `deny` / `log`

Запись библиотеки может ограничивать, какие функции можно вызывать, и
принудительно маскировать результаты (всё опционально):

```yaml
libraries:
  - use: '@std/random@v1'
    capabilities: []      # обязательно в каждой записи; [] = без разрешений
    secret: true          # маскировать каждый результат этой библиотеки в логе запуска
    allow: [uuid4, ulid]  # белый список: остальные вызовы проваливают шаг
    deny: [email]         # чёрный список: побеждает allow
    log: [uuid4]          # всегда маскировать результаты этих функций
```

- `deny:` побеждает `allow:`, если имя встречается в обоих; заблокированный
  вызов проваливает шаг с сообщением, называющим правило, а `perfscale lint`
  помечает его в токенах `${alias.fn(...)}`.
- Маскирование **аддитивно**: результат маскируется, если функция объявляет
  `secret: true` в своих метаданных, запись задаёт `secret: true` или функция
  находится в списке `log:` записи. Способа *снять* маску намеренно нет.
  Замаскированные значения записываются в реестр секретов запуска и
  отображаются как `***` в логе запуска; полезная нагрузка по сети сохраняет
  реальное значение.
- Каждое имя в `allow:`/`deny:`/`log:` должно быть функцией, которую
  библиотека действительно экспортирует, — опечатка — жёсткая ошибка
  валидации (иначе она молча никогда бы не сработала).

- Локальные пути (`use: ./libs/fixer-ids.wasm`) загружают библиотеки
  WASM-компонентов (WASI Preview 2, WIT `perfscale:library@0.2.0` —
  компоненты, собранные под старый ABI `@0.1.x`, продолжают загружаться,
  просто они никогда не видят настройки запуска; см.
  [RFC 005](../rfcs/005-libraries.md)). Пути разрешаются **относительно
  директории объявляющего файла**, как пути `import:`. Бинарник perfscale CLI
  поставляется с поддержкой WASM; встраивающим `perfscale-core` нужна
  cargo-фича `wasm-libs`.

Удалённые источники (`https://…` и `git+…`) — это **ссылки на дистрибуцию** —
они никогда не скачиваются во время запуска. `perfscale install <files>`
скачивает каждую удалённую библиотеку один раз, проверяет её дайджест,
складывает в контентно-адресуемый кэш (`<cache>/libraries/<sha256>.wasm`) и
пишет `perfscale.lock` рядом с объявляющим файлом. `perfscale run` и
`perfscale lint` затем разрешают каждую удалённую ссылку через lock + кэш,
**полностью офлайн**: отсутствующий lock, отсутствующая запись или
отсутствующий артефакт в кэше — жёсткая ошибка с указанием запустить
`perfscale install`.

```yaml
# HTTPS: sha256 закрепляет артефакт — переопубликованный артефакт с другим
# дайджестом — жёсткая ошибка, никогда не молчаливая подмена. Закрепление
# опционально: без него `perfscale install` закрепляет вычисленный дайджест
# в lock-файле и печатает предупреждение с советом добавить его сюда.
- use: 'https://vendor.example.com/fixer-ids.wasm'
  sha256: '9f2c…(64 hex)…'

# git: URL репозитория + ref (тег/ветка/коммит) + путь к артефакту внутри репозитория.
# Ref разрешается в коммит во время установки и закрепляется вместе с
# дайджестом артефакта; `perfscale install --refresh` разрешает его заново.
- use: 'git+https://github.com/org/repo.git@v1.2.3#libs/fixer-ids.wasm'
```

`perfscale.lock` — это TOML, ключованный точной строкой `use:`, и он
предназначен для коммита:

```toml
version = 1

[[libraries]]
use = "https://vendor.example.com/fixer-ids.wasm"
sha256 = "…"

[[libraries]]
use = "git+https://github.com/org/repo.git@v1.2.3#libs/fixer-ids.wasm"
commit = "…resolved sha…"
sha256 = "…artifact digest…"
```

Замечания:

- Кэш учитывает `PERFSCALE_CACHE_DIR` (затем `XDG_CACHE_HOME/perfscale`,
  по умолчанию `~/.cache/perfscale`) — тот же корень, что и кэш git-клонов
  для `import:`.
- Библиотеки, объявленные в документе, импортированном из git
  (`import: { git: … }`), закрепляются в `perfscale.lock` **внутри того
  репозитория** (в его корне); запустите `perfscale install` для
  импортирующего файла, и он запишется туда. Install следует по цепочкам
  `import:` (включая удалённые) именно по этой причине.
- Для ссылок `git+` YAML-ключ `sha256:` опционален: закреплённый коммит —
  якорь целостности. Если он задан, install проверяет его, и несовпадение —
  жёсткая ошибка.

#### AOT-компиляция (burn-кэш) и `perfscale burn`

Компиляция WASM-компонента (Cranelift) стоит реального времени при каждом
`run`/`lint` — секунды для больших компонентов. Два механизма убирают её:

- **Burn-кэш.** `perfscale install` предкомпилирует каждую объявленную
  WASM-библиотеку — удалённую *и* локальную `./path.wasm` (локальные
  библиотеки не получают записи в `perfscale.lock`; сам файл уже локален) —
  в `<cache>/libraries/<sha256>.cwasm`. Загрузчик сначала проверяет этот кэш
  и десериализует артефакт (нативный код, быстрый mmap); при любом промахе
  или несовпадении он молча откатывается на полную компиляцию, так что кэш
  чисто опционален. Артефакты несут заголовок, закрепляющий версию wasmtime,
  целевой триплет, конфигурацию движка и дайджест исходника: **обновление
  perfscale инвалидирует их — перезапустите `perfscale install`, чтобы
  перепрожечь**.
- **Встраивание в бинарник.** `perfscale burn -f test.yaml [-c config.yaml] -o
  ./perfscale+libs` пишет копию запущенного бинарника с дописанными
  `.cwasm`-артефактами библиотек документов (трейлер `PFSEMBED` — без
  патчинга исполняемых секций, работает для ELF/Mach-O/PE). Производный
  бинарник разрешает эти библиотеки из самого себя по точной строке `use:`,
  поэтому работает **без `.wasm`-файлов, кэша и `perfscale.lock` на диске** —
  один файл для доставки на генераторы нагрузки. Удалённые ссылки должны быть
  сначала установлены. Поскольку встраивание запекает артефакты, прожжённый
  бинарник, обнаруживший несовпадение заголовка, падает с ошибкой
  «перепрожгите», а не откатывается; перезапустите `perfscale burn` с текущим
  perfscale.

Что burn **не** меняет: накладные расходы на вызов (JSON-маршалинг
аргументов, store/память на экземпляр на VU) неизменны — burn убирает
компиляцию на запуск, а не стоимость вызова.

Правила WASM-библиотек:

- Песочница fail-closed: WIT-импорты компонента инспектируются при загрузке,
  и всё, что выходит за выдачу `capabilities:` в YAML, — жёсткая ошибка
  загрузки с указанием нужных и выданных capability — если только `info()`
  компонента не объявляет `"pure": true`; в этом случае импорты
  `wasi:filesystem` / `wasi:clocks/wall-clock` прощаются как шум тулчейна
  (гость всё равно не получает preopen'ов, поэтому реальный доступ к файлам
  падает в рантайме). `fs` — это read-only preopen, ограниченный `fs_root`
  (по умолчанию: директория, содержащая `.wasm`); `clock` — это
  `wasi:clocks`; `net: [hosts]` **пока не поддерживается** (выдача `net`
  проваливает загрузку с понятной ошибкой); `wasi:random` и сырые сокеты не
  предоставляются никогда — библиотеки берут случайность из PRNG с seed
  (`ctx.seed`) в своём SDK.
- `with:` передаётся в `init()` компонента как JSON; сбой init фатален для
  запуска.
- Трап или бесконечный вызов проваливает шаг: каждый вызов выполняется под
  бюджетом fuel (~50M), а каждый экземпляр ограничен 64 МиБ памяти.
- Файл компонента может быть не больше 64 МиБ при загрузке (тот же лимит, что
  `perfscale install` применяет к удалённым скачиваниям) — память компиляции
  масштабируется с размером модуля, и лимит применяется раньше, чем
  ограничения fuel/памяти смогут.
- Кэш артефактов проверяется во время запуска, а не только при установке:
  закэшированный `.wasm`, чьи байты больше не хешируются в закреплённый
  дайджест (повреждение или подделка), — жёсткая ошибка с указанием
  перезапустить `perfscale install`. Артефакты burn (`.cwasm`, встроенные
  полезные нагрузки) несут заголовок, закрепляющий дайджест исходника, версию
  wasmtime, целевой триплет и конфигурацию движка, и десериализуются только
  после полного совпадения заголовка.
- Пишите библиотеки на Rust с
  [`perfscale-library-sdk`](../crates/perfscale-library-sdk/README.md).

Функции `@std/random@v1`:

| Функция | Возвращает |
|---|---|
| `uuid4([key])` | Случайный UUID RFC 4122 v4 |
| `uuid7([key])` | Временно́ упорядоченный UUID RFC 9562 v7 (48-битный префикс unix-мс) |
| `ulid([key])` | 26-символьный ULID Crockford-base32 (префикс unix-мс) |
| `nanoid([len], [key])` | URL-безопасный id из `A-Za-z0-9_-` (длина по умолчанию 21) |
| `int(a, b, [key])` | Случайное целое в `[a, b]` включительно |
| `float(a, b, [dp], [key])` | Случайное число в `[a, b]`, `dp` знаков после запятой (по умолчанию 2) |
| `pick(a\|b\|c, [key])` | Случайный выбор среди вариантов, разделённых `\|` |
| `weighted(a:10\|b:90, [key])` | Взвешенный случайный выбор среди пар `значение:вес` |
| `seq(name)` | Именованный монотонный счётчик на экземпляр генератора, начиная с 1 |
| `pattern("ORD-####-????")` | Заполнение шаблона: `#`→цифра, `?`→a-z, `^`→A-Z, `*`→буква или цифра |
| `first_name()` / `last_name()` / `name()` | Случайные имена (небольшие встроенные корпуса) |
| `username()` / `email()` / `company()` | Случайный username / email / компания |
| `lorem([words])` | Слова lorem ipsum (по умолчанию 5) |
| `phone()` | Случайный номер телефона (`+1-NNN-NNN-NNNN`) |
| `date(a, b)` | Случайная дата между `YYYY-MM-DD` a и b включительно, на выходе `YYYY-MM-DD` |
| `timestamp(a, b)` | Случайная метка времени unix-мс в `[a, b]` |
| `datetime(a, b)` | Случайный datetime RFC 3339 между датами a и b (весь конечный день включён) |

### Композиция документов: `import`

И определения тестов, и конфиги принимают верхнеуровневый `import:` с именем
базового документа. База загружается первой (она может импортировать свою
базу, рекурсивно), затем текущий документ глубоко сливается поверх:
**объекты сливаются поключно, скаляры и массивы (включая `steps:`)
заменяются** импортирующей стороной. Единственное исключение — `libraries:`,
который конкатенируется по цепочке, — дублирующийся алиас — ошибка
валидации.

```yaml
# конфиг команды — наследует общий базовый документ организации, переопределяет одну переменную
import: ../shared/_base.yaml
variables:
  region: us
```

Три формы источника:

```yaml
# относительный путь в файловой системе (разрешается относительно директории импортирующего файла)
import: ../shared/_base.yaml

# сырой HTTP(S) URL — закрепите ref в пути
import: "https://raw.githubusercontent.com/org/repo/v1.2.0/perf/config/_base.yaml"

# любой git-хост (SSH или HTTPS remote, включая self-hosted)
import:
  git: git@gitlab.example.com:group/repo.git
  ref: v1.2.0          # тег, ветка или SHA коммита
  file: perf/config/_base.yaml
```

Удалённые импорты (URL и git) **fail-closed**: они выполняются только когда
вызывающая сторона передаёт `--allow-remote-import`. Разрешение принадлежит
вызывающей стороне, потому что разрешение импортов происходит до проверок
`allow_file_actions` / `allow_process_actions` — иначе удалённая база могла
бы выдать себе эти права и подтянуть шаг `std/child_process@v1`. Документ
никогда не может сам разрешить себе сеть.

Источники остаются ограниченными: документ, полученный по URL, разрешает
относительные импорты относительно своего собственного URL; документ из
git-репозитория может импортировать только файлы внутри того же клона
(выходы через `../` отклоняются). Удалённый документ никогда не может
прочитать вашу локальную файловую систему. Циклы импортов падают с выводом
цепочки.

Git-импорты клонируются с `--depth 1` через ваш системный `git` (SSH-ключи и
credential helpers применяются) и кэшируются в
`~/.cache/perfscale/imports/`. Теги и SHA коммитов неизменны — кэшируются
навсегда. Ветки ревалидируются по удалённому репозиторию после короткого
TTL, так что `ref: main` следует за веткой; `--refresh-imports` принудительно
перескачивает. Полное руководство — в
[docs/core/imports.md](core/imports.md).

### Инициализация и переменные

Шаги `before:` выполняются **один раз**, по порядку, до старта любого VU —
для одноразовой инициализации вроде получения токена или построения профиля
соединения. Каждый шаг `before` — обычный шаг (`use`/`with`/`outputs`); его
имя в `outputs` доступно **каждому** тестовому шагу в пространстве имён
`config`. `variables:` хранит статические значения, доступные в `vars`.

```yaml
vus: 50
variables:
  region: eu-west
before:
  - uses: std/http@v1
    with:
      method: POST
      url: "https://api.example.com/token"
      body: { user: demo, region: "${{ vars.region }}" }
    outputs: auth            # ← доступен тестовым шагам как config.auth
```

```yaml
# test.yaml
steps:
  - uses: std/http@v1
    with:
      url: "https://api.example.com/me"
      headers:
        authorization: "Bearer ${{ config.auth.body }}"   # из шага before
        x-region: "${{ vars.region }}"                      # из variables
```

- `before` выполняется независимо от `--quiet` (его сбои всегда печатаются).
  Если любой шаг инициализации падает, запуск **прерывается до запуска VU** —
  сломанная инициализация привела бы к одинаковому провалу каждой итерации.
- Шаги `before` видят `${{ vars.* }}` и выводы предыдущих шагов инициализации
  (под их собственными именами `outputs`). Тестовые шаги видят `config.*` и
  `vars.*`, но не выводы друг друга.
- Интерполяция всегда даёт **строку**, поэтому числовое значение конфига
  вроде `${{ config.fix_config.port }}` доходит до действия как `"1111"`.
  Действия, принимающие числа, принимают и строковую форму.

Полный жизненный цикл (включая фоновые процессы, запущенные в `before:`) —
см. [Инициализация и завершение](core/setup-teardown.md).

### Завершение (`after:`)

Шаги `after:` выполняются **один раз** после остановки нагрузки — при
нормальном завершении, при провалившемся запуске, при провалившемся `before:`
и при Ctrl-C/SIGTERM одинаково. Они видят те же `${{ config.* }}` и
`${{ vars.* }}`, что и тестовые шаги. В отличие от `before:`, провалившийся
шаг завершения логируется, но не прерывает оставшиеся (очистка по принципу
best-effort). Типичный шаг `after:` — `std/kill_process@v1` для сервера,
запущенного в `before:`:

```yaml
allow_process_actions: true

before:
  - name: web
    uses: std/child_process@v1
    with:
      command: python3
      args: ["-m", "http.server", "8080"]
      port: 8080
      waitUntil: { port_open: 8080, timeout: 10s }
    outputs: web

after:
  - name: stop web
    uses: std/kill_process@v1
    with: { name: web, signal: TERM }
```

Процессы, ещё живые после шагов `after:`, останавливаются автоматически, так
что явный kill — про чистую и своевременную остановку, а не про
предотвращение утечек. См. [`std/child_process@v1`](core/actions.md#stdchild_processv1)
для полного списка параметров (политика рестарта, захват вывода, `waitUntil`),
[examples/with-processes.config.yaml](../examples/with-processes.config.yaml)
для готового примера и [Инициализация и завершение](core/setup-teardown.md)
для всего жизненного цикла (прерывания, авто-kill, поток данных).

`after:` — также дом для SLO-порогов уровня запуска: `std/thresholds@v1`
вычисляет выражения в стиле k6 (`p95<500`, `rate<0.05`, `count==0`) по
метрикам, собранным за весь запуск, один раз и проваливает запуск (ненулевой
код выхода), когда нарушен порог с `severity: fail`:

```yaml
after:
  - name: slo gate
    use: std/thresholds@v1
    with:
      db_query_duration: ["p95<500", "max<2000"]
      db_query_failed: ["rate<0.05"]
      db_errors: ["count==0"]
    severity: fail            # fail (по умолчанию) | warn | info
    message: "checkout SLO"   # необязательно, интерполируется
```

См. [`std/thresholds@v1`](core/actions.md#stdthresholdsv1) для грамматики
выражений, видов метрик и поля `thresholds` в JSON сводки запуска.

С `--locust` тот же конфиг отображается в `--users`/`--spawn-rate`/`--run-time`
locust. С `--k6` конфигурация нагрузки живёт в собственном блоке `options`
скрипта, а конфиг-файл игнорируется.

## Валидация без запуска: `perfscale lint`

Проверяйте файлы заранее — в CI, pre-commit-хуках или прямо во время
написания:

```sh
perfscale lint test.yaml config.yaml
```

Помимо валидации по схеме, `lint` помечает неизвестные и опечаточные имена
полей с подсказками «возможно, вы имели в виду» (`chek` → `check`, `vsu` →
`vus`, `std/htp@v1` → `std/http@v1`), включая параметры `with:` для
конкретных действий. См.
[Команды CLI → lint](cli/commands.md#perfscale-lint).

## Ошибки валидации

perfscale валидирует перед запуском. Примеры того, что вы увидите:

```text
error: schema validation failed:
  /steps/0 — every step must name an action: `use: std/http@v1` (or the `uses:` alias)
```

```text
error: invalid YAML: found unexpected end of stream
```

Перегенерируйте схемы после изменения Rust-типов:

```sh
cargo run -p perfscale-core --example gen_schema
```

(Тест CI `shipped_schemas_match_generated_ones` падает, если `schema/`
устарел.)
