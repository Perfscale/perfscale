# Бенчмарки

perfscale поставляется с бенчмарк-скриптом на основе наборов тестов (suites),
сравнивающим движки под идентичной нагрузкой:

```sh
./scripts/bench.sh                       # all suites
SUITES="throughput startup" ./scripts/bench.sh
```

Каждый сценарий сравнения движков обращается к одному и тому же экземпляру
`perfscale serve` на loopback, поэтому любая разница между строкой
`perfscale (*)` и её «родным» аналогом — это накладные расходы обёртки
perfscale, а не самого инструмента. Отдельные наборы `specjbb` и `renaissance`
вместо этого запускают собственные JVM-бенчмарки.

| Сценарий | Что выполняется |
|---|---|
| `locust (native)` | `locust`, вызванный напрямую — базовый уровень |
| `k6 (native)` | `k6`, вызванный напрямую — базовый уровень |
| `jmeter (native)` | `jmeter -n -t`, вызванный напрямую — базовый уровень (только наборы overhead/startup) |
| `sytester (10000 TPS)` | [SyTester](https://gitverse.ru/sbertech/sytester) Community Edition через его REST API — базовая линия (таблицы throughput, saturation, grpc и db). VU-модели у него нет, поэтому он подаёт свою максимальную фиксированную интенсивность (`SYT_RATE`) |
| `gcannon (native)` | [gcannon](https://github.com/MDA2AV/gcannon) — io_uring-генератор HTTP/1.1 из HttpArena (только Linux), таблицы throughput и saturation; одно keep-alive соединение на VU, без pipelining, потоков = ядер |
| `zrk (native)` | [zrk](https://github.com/zoxy-io/zrk) — генератор HttpArena с открытой моделью и коррекцией coordinated omission: `--closed` в таблицах throughput и saturation (та же модель, что у остальных строк), `-R` с фиксированной частотой в таблице latency |
| `perfscale (k6)` | тот же скрипт k6 через `perfscale run --k6` |
| `perfscale (locust)` | тот же locustfile через `perfscale run --locust` |
| `perfscale (jmeter)` | тот же `.jmx`-план через `perfscale run --jmeter` (только наборы overhead/startup) |
| `perfscale (yaml)` | собственный шаговый движок perfscale (без внешних бинарников) |
| `perfscale (yaml quiet)` | шаговый движок с `--quiet` — логирование каждого запроса отключено; разница с `perfscale (yaml)` — это стоимость логирования |

## Наборы тестов (suites)

| Набор | На какой вопрос отвечает |
|---|---|
| `overhead` | Добавляет ли обёртка время выполнения при фиксированной длительности? (hyperfine, статистическое усреднение) |
| `throughput` | Сколько запросов и с какой задержкой реально обеспечивает каждый сценарий? Плюс CPU, CPU на запрос, пиковый RSS и операции ввода-вывода из того же инструментированного прогона |
| `startup` | Сколько стоит запуск обёртки? (прогоны по 1 с, где старт не «тонет» в длительности теста) |
| `scaling` | Как растут RPS / p95 / RSS с ростом числа VU? (стандартная развёртка: 10, 50, 200) |
| `saturation` | Приблизительный максимум RPS на движок при большом числе VU (по умолчанию 256) |
| `latency` | Фиксированная частота прихода (`LAT_RATE`, по умолчанию 10000 req/s через `LAT_CONNS` = 256 соединений/VU в течение `LAT_DURATION` = 20s): задержка с коррекцией CO, отсчитанная от запланированного старта запроса — zrk `-R` против perfscale `arrival.co_correct: true` и arrival по умолчанию, отбрасывающего итерации при насыщении (его колонка `Dropped` — это та задержка, которую двое других показывают вместо отбрасывания) |
| `yaml` | Сколько стоит каждая возможность нативного движка? (базовый GET против `--quiet` против +check против POST-тела против многошаговой подстановки) |
| `ws` | Пропускная способность WebSocket-сообщений и RTT: эхо-запросы по одному соединению к эндпоинту `/ws` сервера `serve` (`perfscale (yaml)`, `k6 (native)`, `perfscale (k6)` — у locust нет встроенной поддержки WebSocket, он пропускается) |
| `boundary` | Где движок ломается? Лестница потолков VU (`BOUNDARY_LADDER`, по умолчанию `5000 15000 30000`): на каждой ступени разгон 0→потолок за `BOUNDARY_DURATION`; граница — уровень VU / время / RPS, при которых накопленная доля ошибок впервые достигает `BOUNDARY_ERR_PCT` процентов (по умолчанию 1%), либо ступень, на которой процесс умирает (OOM/краш считается границей). Пересёкший движок дальше не поднимается. Таблица также показывает **достигнутую нагрузку** на последней ступени: фактически заспавненные VU, RPS, p95, пиковый RSS и CPU — чтобы `never crossed` было оценено в цифрах, а не просто констатировано |
| `tls` | «Налог» TLS: та же нагрузка против `perfscale serve --tls` (самоподписанный HTTPS, проверка отключена) |
| `library` | Стоимость WASM-библиотек значений: компиляция на каждый прогон (холодный кэш) против десериализации burn-кэша против встроенной `@std/random` |
| `grpc` | Унарный вызов `std/grpc@v1` против примера `grpc_echo_server` из репозитория |
| `graphql` | Один и тот же GraphQL POST от `std/graphql@v1`, транспортного `std/http@v1`, стокового k6 и k6 через perfscale против примера `graphql_server` из репозитория — xk6 не нужен |
| `db` | SQL: холодный connect+query против тёплых VU-scoped соединений против транзакций (`std/db-*@v1`, PostgreSQL по `BENCH_PG_DSN` — каждая строка ходит в тот же реальный сервер), плюс тёплая форма от locust (psycopg2), JMeter (JDBC) и k6 — строка k6 использует **кастомный бинарь**, собранный с расширением `xk6-sql` и postgres-драйвером (в стоковом k6 SQL-модуля нет), и только она его использует |
| `sharedvars` | Общее изменяемое состояние между VU — передача объектов create → update → delete. Каждый движок крутит одинаковый цикл своим механизмом, без сети: **churn** (append → pop → increment) и **drain** (очередь предзаполнена `SV_PREFILL` элементами, pop → increment). Кроме итераций/с проверяет корректность: **Lost** = итерации − финальный счётчик, **Queue Δ** = остаток − ожидаемое (до VUS — итерации, оборванные дедлайном, больше — гонка). perfscale `shared_variables` (memory-драйвер, атомарные операции); **k6 через кастомный бинарь с xk6-kv** (`K6_KV_BIN`; в xk6-kv нет атомарных pop/increment, поэтому забор — `list`+`delete`, счётчик — `get`+`set`); locust (deque на уровне модуля — один процесс, кооперативные greenlet'ы); JMeter (`props` с `ConcurrentLinkedQueue` + `AtomicLong` из JSR223 Groovy) |
| `sourceips` | Снимает ли `source_ips` потолок соединений на один эндпоинт? `SRC_VUS` (по умолчанию 6000) VU держат по одному keep-alive соединению (`pool: dedicated` + think time 1s) при диапазоне эфемерных портов, суженном до `SRC_PORT_RANGE` (по умолчанию `50000 53999` — 4000 портов; sysctl на всю машину, восстанавливается после), сначала с одного IP источника, затем с `SRC_IPS_COUNT` (по умолчанию 4) loopback-адресов. Показывает пик установленных соединений (`ss`), ошибки соединения, RPS. Linux + sudo без пароля (CI-раннер); в остальных случаях пропускается |
| `pubsub` | Pub/sub: пропускная способность publish и e2e-латентность roundtrip pub/sub (`std/pubsub@v1`) против NATS-брокера (`BENCH_NATS_URL` — каждая строка ходит в тот же реальный брокер) в позициях `scope: exchange` (соединение на итерацию) и `scope: vu` (одно соединение на VU, с fire-and-forget двойником `flush: none`), плюс строки k6 через **кастомный бинарь** с расширением xk6-nats (в стоковом k6 NATS-модуля нет) в тёплой (соединение на VU) и холодной (соединение на итерацию — честный двойник `scope: exchange`) позициях |
| `specjbb` | **Только по явному выбору** (никогда не входит в список по умолчанию): [SPECjbb2015](https://www.spec.org/jbb2015/) — отдельный коммерческий Java-бенчмарк, не HTTP-цель и не конкурент генераторам нагрузки. Показывает родные max-jOPS / critical-jOPS (Java-операции/с — **не** HTTP RPS), а также режим, длительность, CPU и пиковый RSS |
| `renaissance` | Набор [Renaissance](https://renaissance.dev/) (MIT-дистрибутив; JVM-нагрузки; по умолчанию `finagle-http`): пропускная способность операций бенчмарка (ops/s — **не** HTTP RPS) и время операции, а также длительность, CPU и пиковый RSS. Входит в ежедневный CI-прогон из закреплённого, проверенного по sha256 релизного jar |

JMeter участвует только в наборах hyperfine (`overhead`/`startup`): харнес
бенчмарков по-прежнему читает его консольные дельты, поэтому он не попадает
в таблицу `throughput`, хотя сам `perfscale run --jmeter` теперь разбирает
`.jtl` прогона в полные метрики с перцентилями.

Набор `graphql` выполняет один и тот же POST четырьмя способами для честного
сравнения: `perfscale (graphql)` (`std/graphql@v1` — разбор документа и
валидация по схеме, интроспекция запрашивается один раз за прогон),
`perfscale (http)` (только транспорт, `std/http@v1`), `k6 (native)` и
`perfscale (k6)`. Стоковый k6 и строка `std/http` не выполняют валидацию на
клиенте; нативные строки Perfscale запускаются с `--quiet`, чтобы
соответствовать строкам k6. Обычный `http.post` не требует расширений xk6,
поэтому строки используют стоковый k6.

Наборы выбираются через `SUITES="..."`. Сценарии, чей движок (`k6`/`locust`/
`jmeter`) отсутствует в `PATH`, пропускаются, а не считаются упавшими;
`overhead`/`startup` требуют
[hyperfine](https://github.com/sharkdp/hyperfine), остальные — нет.

Набор `boundary` определяет пересечение границы по-разному для каждого
движка: k6 сам прерывается через порог `abortOnFail` (границей считается
строка прогресса на пике VU), locust читается из строк Aggregated в
`--csv-full-history`, jmeter — из накопленных дельт `summary +` (запускается с
`-Jsummariser.interval=2`, heap поднимается через `BOUNDARY_JMETER_HEAP`), а
нативный движок — из периодических строк `[stats]` — поэтому строка нативной
границы выполняется без `--quiet` и включает стоимость логирования каждого
запроса. Ненулевой код выхода движка без обнаруженного пересечения (OOM,
краш) фиксируется как граница на текущей ступени с пометкой «process died».
Строки для обёрнутых locust/jmeter опущены: обёртка — это просто
проксирование, а граница — свойство движка. `BOUNDARY_MAX_VUS`, если задан,
заменяет лестницу одной ступенью (обратносовместимый вариант). Между
прогонами набор проверяет цель 50 свежими соединениями и ждёт, пока на
loopback рассосутся TIME_WAIT-сокеты предыдущего движка (на CI-раннере также
расширяется `ip_local_port_range` и включается `tcp_tw_reuse`) — граница
должна быть границей движка, а не исчерпанных эфемерных портов машины. На
последней ступени, которую движок выполнял (верх лестницы либо ступень
пересечения/падения), отчёт добавляет колонки достигнутого: фактически
заспавненные VU (строки прогресса k6, User Count locust, пик `vus` в сводке
нативного движка — консоль JMeter не сообщает число потоков), RPS (средний
за прогон для k6/JMeter/native, скорость в конце рампы для locust), p95 (у
JMeter его нет в консольной сводке), плюс пиковый RSS и CPU из
`/usr/bin/time` — «never crossed» не значит «бесплатно», и эти колонки
показывают цену верхней ступени.

Набор `db` разделяет холодный путь (`perfscale (cold)`,
`perfscale (cold, params)`: connect + один запрос
на итерацию, соединение закрывается в конце итерации) и тёплый
(`perfscale (warm vu, …)`:
одно соединение `scope: vu` на VU — вызов `db-connect` в каждой итерации
переиспользует припаркованное соединение за ~0 мс — `DB_WARM_QUERIES`
запросов на итерацию, без `db-close`, та же форма «один коннект на VU», что
и у строк конкурентов; `perfscale (warm vu+prepared, …)` добавляет
`prepared: true` + `store_rows: false` — потолок движка;
`perfscale (warm vu+prepared+rows, …)` — то же самое с `store_rows: true`,
так что разница между двумя tuned-строками изолирует стоимость
JSON-материализации строк;
`perfscale (warm tx, …)`: `DB_TX_CYCLES` × begin+query+commit).
In-process SQLite-строк нет: каждая строка ходит в тот же реальный
PostgreSQL, что и конкуренты, — сравнение делит зависимость. Строка locust
(`pipx inject locust psycopg2-binary`) и строка JMeter (PostgreSQL JDBC jar в
`lib/` JMeter, переменная `BENCH_PG_JDBC_JAR` для другого пути) и строка k6
повторяют тёплую форму. Строка `k6 (xk6-sql, warm)` — это **не стоковый k6**: в
нём нет SQL-модуля, поэтому bench-workflow собирает отдельный бинарь через
`xk6 build` (расширение xk6-sql + postgres-драйвер, все версии зафиксированы,
бинарь кэшируется; `K6_SQL_BIN`, по умолчанию `target/xk6-sql/k6`). Версия
ядра k6 внутри может отличаться от стоковой — сводка окружения в CI печатает
обе. Кастомный бинарь обслуживает только эту строку; все остальные сценарии
k6 продолжают использовать стоковый.

Набор `pubsub` публикует одно сообщение фиксированного размера
(~`PUBSUB_PAYLOAD_BYTES`, по умолчанию 256 байт) за итерацию. Каждая строка
ходит в тот же реальный брокер — in-process строк с драйвером `memory` нет,
сравнение делит зависимость со строками k6. Строки `nats` публикуют в брокер по
`BENCH_NATS_URL` (по умолчанию `nats://127.0.0.1:4222`; локально
`docker run -d -p 4222:4222 nats:2.15-alpine`, в CI — service-контейнер) и
платят connect + publish + flush за итерацию при `scope: exchange` по
умолчанию — **cold**-строки (стоимость соединения входит в измерение и
видна отдельно в `pubsub_connect_ms`); **warm**-строки (`scope: vu`)
переиспользуют одно соединение на VU — «тёплая» позиция k6. Тёплые строки
используют `flush: message` по умолчанию (flush + ожидание ack брокера на
итерацию, `pubsub_publish_ms` — полный round trip); строка
`perfscale (nats, publish, warm, flush=none)` публикует в режиме
fire-and-forget (измеряется постановка в очередь, без ожидания ack) — ровно
позиция клиента k6 xk6-nats, который ack не ждёт никогда. Строки
`pub/sub e2e` сначала подписываются, публикуют одно сообщение с маркером в
per-VU сабжект (`bench.pubsub.vu${vu}`) и ждут именно его; `e2e p95` —
брокерский round trip. Строки `k6 (xk6-nats)` — это **не стоковый k6**:
кастомный бинарь с расширением xk6-nats (форк rongfengliang от
ydarias/xk6-nats — Pondigo/xk6-nats вообще не регистрирует свой модуль и
не импортируется; форк закреплён на k6 v1.3.0 по v1-пути модуля, который
несовместим с ядром go.k6.io/k6/v2 у xk6-sql, отсюда второй бинарь:
`K6_NATS_BIN`, по умолчанию `target/xk6-nats/k6`, собирается bench-workflow).
**warm** держит одно соединение на VU (init scope, позиция xk6-sql в наборе
db); **cold** соединяется на каждую итерацию — честный двойник cold-строки
perfscale nats. Строки roundtrip для k6 нет намеренно: расширение вызывает
subscribe-обработчик из горутины доставки nats.go, что гоняется с
JS-рантаймом VU и под нагрузкой периодически роняет весь процесс k6 — e2e на
k6 этим расширением не измеряется, поэтому e2e-латентность только нативная.
Латентности k6 имеют гранулярность `Date.now()` (1 мс), поэтому
субмиллисекундные publish-замеры читаются как 0 — там сравнивайте Msg/s, а
латентность — по нативным строкам.

Строки SyTester управляют им через REST API: каждая строка поднимает JVM
(`SYTESTER_JAVA`, Java 21+) из релизного jar (`SYTESTER_JAR`, по умолчанию
`target/sytester/SyTester.jar` — bench-workflow скачивает закреплённый jar
v6.10.0 и сверяет sha256), гоняет незаписываемый прогрев `SYT_WARMUP` (по
умолчанию 5s) с той же интенсивностью, затем план на длительность таблицы,
читает `/action/lastReport` и гасит JVM. Планы повторяют примеры SyTester:
`GENERATOR` GET для throughput/saturation, `GENERATOR` gRPC unary для grpc
(`echo.proto` загружается как proto set; пул отправителей
`grpc.maxConnections` = `SYT_MAX_VUS`) и `STEPS` `TPS_LOADER` с PgJDBC
`SELECT 1` для db. Во всех планах большой `errorsToStop`: значение по
умолчанию (100) обрывает план в первую же секунду проблем, а бенчу нужен
процент ошибок. CPU на запрос и пиковый RSS покрывают всю жизнь JVM.
`failedPercentage` остаётся 0 при транспортных ошибках (статус `-1`),
поэтому `Err` считается из числа упавших запросов; латентности — в целых
миллисекундах. Локально: скачайте jar со
[страницы релизов](https://gitverse.ru/sbertech/sytester/releases) и
запустите `SUITES=throughput SYTESTER_JAR=… SYTESTER_JAVA=… ./scripts/bench.sh`.

Микробенчмарки горячих путей нативного движка (парсинг YAML, подстановка
`${{ ... }}`, запись метрик / перцентильная сводка, захват вывода процессов
через `RingBuf`, матчеры готовности `waitUntil`) находятся в
`crates/perfscale-core/benches/` и запускаются командой `cargo bench -p perfscale-core`.

## SPECjbb2015 (только по явному выбору)

Набор `specjbb` запускает [SPECjbb2015](https://www.spec.org/jbb2015/) —
отдельный коммерческий Java-бенчмарк серверов, **не** HTTP-цель и не
конкурент генераторам нагрузки, — поэтому он никогда не попадает в таблицы
сравнения движков и не входит в список наборов по умолчанию (и в умолчание
CI). Выбирается явно:

```sh
SPECJBB_HOME=/opt/SPECjbb2015 SUITES=specjbb ./scripts/bench.sh
```

Дистрибутив не поставляется и не скачивается. Укажите его через
`SPECJBB_HOME` (корень комплекта с `specjbb2015.jar`) или `SPECJBB_JAR`
(прямой путь к jar); дополнительные параметры: `SPECJBB_JAVA` (запускалка
java), `SPECJBB_MODE` (по умолчанию `COMPOSITE`; есть `MULTI`/`DIST`),
`SPECJBB_JAVA_ARGS` и `SPECJBB_ARGS`. Если `specjbb` не выбран — набор
молча пропускается, есть комплект или нет; если выбран, а путь неверен —
бенчмарк падает с понятной ошибкой, а не показывает фиктивный успех.

Раннер (`scripts/bench_specjbb2015.sh`) выполняет официальный jar из корня
комплекта — `java -jar specjbb2015.jar -m <MODE>` — под тем же замером
ресурсов через `/usr/bin/time`, что и остальные строки, и никогда не
укорачивает официальный прогон. В отчёт добавляется отдельная секция с
родными **max-jOPS** и **critical-jOPS** (Java-операции/с — это НЕ HTTP RPS,
сравнивать с таблицами движков их нельзя), а также режимом, длительностью,
CPU и пиковым RSS; те же поля попадают в `bench-results.json` (набор
`specjbb`). `bench_compare.py` сравнивает jOPS только между прогонами одного
режима. Консольный лог и дерево отчётов SPEC сохраняются как артефакты в
`specjbb-artifacts/` (переопределяется `SPECJBB_RESULTS_DIR`; выгружаются
вместе с артефактом bench CI), а при завершении JVM убивается — процессов
java не остаётся.

## Renaissance (MIT-дистрибутив)

Набор `renaissance` запускает MIT-дистрибутив набора
[Renaissance](https://renaissance.dev/) — JVM-нагрузки (Big Data,
конкурентность, функциональные), **не** HTTP-цель — поэтому его строки
никогда не входят в таблицы сравнения движков. Он ВХОДИТ в список наборов по
умолчанию и в ежедневный CI-прогон: закреплённый релизный jar
(`renaissance-mit-0.16.2.jar`, проверенный по sha256) кэшируется CI в
`target/renaissance/`, так что там никакой настройки не нужно. Локально
скачайте закреплённый jar сами или укажите `RENAISSANCE_JAR`:

```sh
RENAISSANCE_JAR=target/renaissance/renaissance-mit-0.16.2.jar SUITES=renaissance ./scripts/bench.sh
```

Раннеру (`scripts/bench_renaissance.sh`) нужна Java 11+ (в CI — 21;
`RENAISSANCE_JAVA` выбирает launcher). Ручки: `RENAISSANCE_BENCHMARKS`
(через пробел; по умолчанию `finagle-http` — один вызов harness на бенчмарк,
по строке отчёта на каждый) и `RENAISSANCE_RUN_SECONDS` (по умолчанию 60 —
собственный предел harness `--run-seconds` на измеряемую фазу плюс прогрев
бенчмарка). Отсутствующий/неверный jar, сбой Java или пустой файл результатов
— ошибка прогона, никакого ложного успеха.

Отчёт получает отдельную секцию: на бенчмарк — пропускная способность
измеряемой операции (**ops/s** — НЕ HTTP RPS) и время операции
(среднее/мин/макс, мс), а также повторения, длительность, CPU и пиковый RSS;
те же поля попадают в `bench-results.json` (набор `renaissance`).
`bench_compare.py` сравнивает только строки одного и того же бенчмарка.
Консольный лог и родной JSON harness (`format_version` 6,
`data.<benchmark>.results[]` с `duration_ns`/`uptime_ns` на операцию)
сохраняются как артефакты в `renaissance-artifacts/` (переопределяется
`RENAISSANCE_RESULTS_DIR`; выгружаются вместе с артефактом bench CI),
scratch-каталоги harness ограничены и удаляются, а при завершении JVM
убивается.

## Методология

- **Цель**: экземпляр `perfscale serve` на loopback (`GET /health`; набор
  `ws` использует его WebSocket-эхо-эндпоинт `GET /ws`) — без сетевого шума,
  одна и та же цель для каждого сценария в рамках прогона. Набор `tls`
  добавляет второй экземпляр `serve --tls`.
- **Сравнение по времени выполнения** (`overhead`, `startup`): hyperfine
  повторяет каждый сценарий (`--runs`, с `--warmup`) и сообщает среднее,
  min/max и стандартное отклонение.
- **Пропускная способность/задержка/ресурсы**: один инструментированный
  прогон на сценарий под `/usr/bin/time` (`-v` на Linux, `-l` на macOS), где
  запросы, RPS и перцентили задержки парсятся из собственной сводки движка
  (текстовая сводка k6, статистика locust `--csv`, единые строки сводки
  perfscale). Один прогон: ориентировочно, без статистической строгости.
- **Осторожно с фиксированной длительностью**: каждый сценарий выполняется
  одинаковое время, поэтому все времена выполнения набора overhead ≈ сама
  длительность. Относительные числа около 1.00 доказывают, что обёртка ничего
  не добавляет; реальные различия между движками — в числах *пропускной
  способности*.
- **Общий CPU**: генератор нагрузки и `perfscale serve` делят одну машину.
  Потолки насыщения включают стоимость цели; если два движка выходят на
  плато при похожих RPS — подозревайте цель/CPU, а не движок.

## Запуск в CI (канонический)

[Workflow `bench`](../.github/workflows/bench.yml) выполняется на
`ubuntu-latest` — фиксированный класс раннера, что устраняет разброс между
локальными машинами:

- **вручную**: GitHub → Actions → `bench` → *Run workflow* (параметры: `vus`,
  `duration`, `runs`, `suites`, `graphql_duration`)
- **еженедельно**: по расписанию, понедельник 04:00 UTC, как проверка дрейфа
  производительности

Сводка задачи содержит таблицу окружения (ОС/CPU/потоки/RAM/swap) и таблицу
ПО (версии perfscale/k6/locust/jmeter/java/hyperfine) перед результатами.
Артефакт `bench-report` (хранится 90 дней) содержит markdown-отчёт и
`bench-results.json`.

### Отслеживание регрессий

Каждый CI-прогон скачивает `bench-results.json` предыдущего успешного прогона
и добавляет в сводку таблицу дельт (`scripts/bench_compare.py`): RPS,
задержка, RSS, накладные расходы на запуск и средние criterion, с пометкой
изменений свыше ±15%. Раннеры — общее оборудование, поэтому регрессии
**предупреждают**, а не роняют задачу — воспринимайте пометку как «посмотри
сюда», подтверждая повторным прогоном.

## Как читать числа

- `overhead`: относительное время выполнения около 1.00 = обёртка бесплатна
  на этой длительности. Реальные различия движков — в `throughput`.
- `throughput`: сравнивайте RPS и перцентили; `CPU per req` нормализует
  стоимость CPU по фактически выполненной работе (движок, потребляющий в 2
  раза больше CPU при в 10 раз большем RPS, *эффективнее*, а не меньше).
- `startup`: `vs native` — собственная стоимость обёртки; `vs ideal` включает
  также старт самого движка.
- Никогда не сравнивайте между машинами или CI-прогонами — только внутри
  одного отчёта (таблица дельт сравнивает между прогонами *на одном классе
  раннеров*, а это наиболее близкое к корректному сравнение).

### Как читать `IO ops` (`in` / `out`)

`N in / M out` — это счётчик файловых операций из прогона под
`/usr/bin/time`:

- **`in`** — операции чтения: блоки, прочитанные *с* файловой системы
  (загрузка скриптов/конфигов, подкачка бинарников). `0 in` — норма для
  тёплого прогона: всё уже в страничном кэше. Холодный первый прогон
  показывает ненулевое `in` (например, k6 подкачивает свой бинарник).
- **`out`** — операции записи: блоки, записанные *на* файловую систему
  (временные скрипты, статистика locust `--csv`, логи).

Единицы IO ops различаются между ОС (GNU time считает блоки ФС на Linux; BSD
time считает блочные операции на macOS), поэтому одно и то же число **не**
означает одинаковый объём байт в разных системах — сравнивайте только внутри
одного отчёта.
