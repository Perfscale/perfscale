# Бенчмарки

perfscale поставляется с бенчмарк-скриптом на основе наборов тестов (suites),
сравнивающим движки под идентичной нагрузкой:

```sh
./scripts/bench.sh                       # all suites
SUITES="throughput startup" ./scripts/bench.sh
```

Каждый сценарий обращается к одному и тому же экземпляру `perfscale serve` на
loopback, поэтому любая разница между строкой `perfscale (*)` и её «родным»
аналогом — это накладные расходы обёртки perfscale, а не самого инструмента.

| Сценарий | Что выполняется |
|---|---|
| `locust (native)` | `locust`, вызванный напрямую — базовый уровень |
| `k6 (native)` | `k6`, вызванный напрямую — базовый уровень |
| `jmeter (native)` | `jmeter -n -t`, вызванный напрямую — базовый уровень (только наборы overhead/startup) |
| `perfscale (k6)` | тот же скрипт k6 через `perfscale run --k6` |
| `perfscale (locust)` | тот же locustfile через `perfscale run --locust` |
| `perfscale (jmeter)` | тот же `.jmx`-план через `perfscale run --jmeter` (только наборы overhead/startup) |
| `perfscale (yaml)` | собственный шаговый движок perfscale (без внешних бинарников) |
| `perfscale (yaml quiet)` | шаговый движок с `--quiet` — логирование каждого запроса отключено; разница с `perfscale (yaml)` — это стоимость логирования |

## Наборы тестов (suites)

| Набор | На какой вопрос отвечает |
|---|---|
| `overhead` | Добавляет ли обёртка время выполнения при фиксированной длительности? (hyperfine, статистическое усреднение) |
| `throughput` | Сколько запросов и с какой задержкой реально обеспечивает каждый сценарий? Плюс CPU, CPU на запрос, пиковый RSS и операции ввода-вывода из того же инструментированного прогона |
| `startup` | Сколько стоит запуск обёртки? (прогоны по 1 с, где старт не «тонет» в длительности теста) |
| `scaling` | Как растут RPS / p95 / RSS с ростом числа VU? (стандартная развёртка: 10, 50, 200) |
| `saturation` | Приблизительный максимум RPS на движок при большом числе VU (по умолчанию 256) |
| `yaml` | Сколько стоит каждая возможность нативного движка? (базовый GET против `--quiet` против +check против POST-тела против многошаговой подстановки) |
| `ws` | Пропускная способность WebSocket-сообщений и RTT: эхо-запросы по одному соединению к эндпоинту `/ws` сервера `serve` (`perfscale (yaml)`, `k6 (native)`, `perfscale (k6)` — у locust нет встроенной поддержки WebSocket, он пропускается) |
| `boundary` | Где движок ломается? Лестница потолков VU (`BOUNDARY_LADDER`, по умолчанию `5000 15000 30000`): на каждой ступени разгон 0→потолок за `BOUNDARY_DURATION`; граница — уровень VU / время / RPS, при которых накопленная доля ошибок впервые достигает `BOUNDARY_ERR_PCT` процентов (по умолчанию 1%), либо ступень, на которой процесс умирает (OOM/краш считается границей). Пересёкший движок дальше не поднимается |
| `tls` | «Налог» TLS: та же нагрузка против `perfscale serve --tls` (самоподписанный HTTPS, проверка отключена) |
| `library` | Стоимость WASM-библиотек значений: компиляция на каждый прогон (холодный кэш) против десериализации burn-кэша против встроенной `@std/random` |
| `grpc` | Унарный вызов `std/grpc@v1` против примера `grpc_echo_server` из репозитория |
| `graphql` | Запрос `std/graphql@v1` против примера `graphql_server` из репозитория |
| `db` | SQL: холодный connect+query против тёплого постоянного пула против транзакций (`std/db-*@v1`, PostgreSQL + in-process SQLite), плюс тёплая форма от locust (psycopg2), JMeter (JDBC) и k6 — строка k6 использует **кастомный бинарь**, собранный с расширением `xk6-sql` и postgres-драйвером (в стоковом k6 SQL-модуля нет), и только она его использует |

JMeter участвует только в наборах hyperfine (`overhead`/`startup`): его
консольная сводка в non-GUI режиме не содержит перцентилей, поэтому он не
попадает в таблицу `throughput`. Парсинг его `.jtl`-файлов результатов для
полных метрик пропускной способности — задача на будущее.

Наборы выбираются через `SUITES="..."`. Сценарии, чей движок (`k6`/`locust`/
`jmeter`) отсутствует в `PATH`, пропускаются, а не считаются упавшими;
`overhead`/`startup` требуют
[hyperfine](https://github.com/sharkdp/hyperfine), остальные — нет.

Набор `boundary` определяет пересечение границы по-разному для каждого
движка: k6 сам прерывается через порог `abortOnFail` (границей считается
строка прогресса на пике VU), locust читается из строк Aggregated в
`--csv-full-history`, jmeter — из накопленных дельт `summary +` (запускается с
`-Jsummariser.interval=2`, heap поднимается через `BOUNDARY_JMETER_HEAP`), а
нативный движок — из периодических строк `[stats]` — поэтому строка нативной
границы выполняется без `--quiet` и включает стоимость логирования каждого
запроса. Ненулевой код выхода движка без обнаруженного пересечения (OOM,
краш) фиксируется как граница на текущей ступени с пометкой «process died».
Строки для обёрнутых locust/jmeter опущены: обёртка — это просто
проксирование, а граница — свойство движка. `BOUNDARY_MAX_VUS`, если задан,
заменяет лестницу одной ступенью (обратносовместимый вариант). Между
прогонами набор проверяет цель 50 свежими соединениями и ждёт, пока на
loopback рассосутся TIME_WAIT-сокеты предыдущего движка (на CI-раннере также
расширяется `ip_local_port_range` и включается `tcp_tw_reuse`) — граница
должна быть границей движка, а не исчерпанных эфемерных портов машины.

Набор `db` разделяет холодный путь (`perfscale (cold)`,
`perfscale (cold, params)`: connect + один запрос
на итерацию, соединение закрывается в конце итерации) и тёплый
(`perfscale (warm pool, …)`:
один постоянный пул на итерацию, `DB_WARM_QUERIES` запросов, `db-close`;
`perfscale (warm tx, …)`: `DB_TX_CYCLES` × begin+query+commit) и добавляет
in-process
SQLite-«пол» (`perfscale (sqlite, …)`, сервер не нужен). Строка locust
(`pipx inject locust psycopg2-binary`) и строка JMeter (PostgreSQL JDBC jar в
`lib/` JMeter, переменная `BENCH_PG_JDBC_JAR` для другого пути) и строка k6
повторяют тёплую форму. Строка `k6 (xk6-sql)` — это **не стоковый k6**: в
нём нет SQL-модуля, поэтому bench-workflow собирает отдельный бинарь через
`xk6 build` (расширение xk6-sql + postgres-драйвер, все версии зафиксированы,
бинарь кэшируется; `K6_SQL_BIN`, по умолчанию `target/xk6-sql/k6`). Версия
ядра k6 внутри может отличаться от стоковой — сводка окружения в CI печатает
обе. Кастомный бинарь обслуживает только эту строку; все остальные сценарии
k6 продолжают использовать стоковый.

Микробенчмарки горячих путей нативного движка (парсинг YAML, подстановка
`${{ ... }}`, запись метрик / перцентильная сводка, захват вывода процессов
через `RingBuf`, матчеры готовности `waitUntil`) находятся в
`crates/perfscale-core/benches/` и запускаются командой `cargo bench -p perfscale-core`.

## GPU-инференс (только локально)

Отдельный набор для бенчмарков **LLM-инференса на GPU** (Ollama /
vLLM через `std/llm@v1`, с метриками прогона `gpu:` — TTFT, токены/сек,
утилизация GPU/VRAM) находится в [`bench/gpu/`](../bench/gpu/README.md). Он
намеренно не входит в CI-workflow выше: на хостовых раннерах нет GPU, поэтому
набор выполняется на локальной машине с картой NVIDIA.

## Методология

- **Цель**: экземпляр `perfscale serve` на loopback (`GET /health`; набор
  `ws` использует его WebSocket-эхо-эндпоинт `GET /ws`) — без сетевого шума,
  одна и та же цель для каждого сценария в рамках прогона. Набор `tls`
  добавляет второй экземпляр `serve --tls`.
- **Сравнение по времени выполнения** (`overhead`, `startup`): hyperfine
  повторяет каждый сценарий (`--runs`, с `--warmup`) и сообщает среднее,
  min/max и стандартное отклонение.
- **Пропускная способность/задержка/ресурсы**: один инструментированный
  прогон на сценарий под `/usr/bin/time` (`-v` на Linux, `-l` на macOS), где
  запросы, RPS и перцентили задержки парсятся из собственной сводки движка
  (текстовая сводка k6, статистика locust `--csv`, единые строки сводки
  perfscale). Один прогон: ориентировочно, без статистической строгости.
- **Осторожно с фиксированной длительностью**: каждый сценарий выполняется
  одинаковое время, поэтому все времена выполнения набора overhead ≈ сама
  длительность. Относительные числа около 1.00 доказывают, что обёртка ничего
  не добавляет; реальные различия между движками — в числах *пропускной
  способности*.
- **Общий CPU**: генератор нагрузки и `perfscale serve` делят одну машину.
  Потолки насыщения включают стоимость цели; если два движка выходят на
  плато при похожих RPS — подозревайте цель/CPU, а не движок.

## Локальный запуск

```sh
cargo build --release
./scripts/bench.sh                                   # all suites, 10 VUs, 15s, 5 runs
VUS=50 DURATION=30s ./scripts/bench.sh
SUITES="yaml" YAML_DURATION=5s ./scripts/bench.sh     # just the native-engine suite
OUTPUT=report.md RESULTS=results.json ./scripts/bench.sh
```

| Переменная | По умолчанию | Описание |
|---|---|---|
| `SUITES` | все | Список наборов через пробел (см. таблицу выше) |
| `VUS` | `10` | Виртуальных пользователей на сценарий |
| `DURATION` | `15s` | Длительность прогона для `overhead`/`throughput` |
| `WARMUP` | `1` | Разогревочные прогоны hyperfine (отбрасываются, не показываются) |
| `RUNS` | `5` | Измеряемых прогонов hyperfine на сценарий |
| `STARTUP_DURATION` / `STARTUP_RUNS` | `1s` / `5` | Длительность прогона / число замеров набора startup |
| `SCALING_VUS` / `SCALING_DURATION` | `10 50 200` / `10s` | Точки развёртки VU / длительность на точку |
| `SAT_VUS` / `SAT_DURATION` | `256` / `15s` | VU насыщения / длительность прогона |
| `YAML_DURATION` / `TLS_DURATION` | `10s` / `10s` | Длительность на сценарий в этих наборах |
| `LIB_DURATION` / `GRPC_DURATION` / `GQL_DURATION` | по `10s` | Длительность на сценарий в наборах library / grpc / graphql |
| `WS_DURATION` / `WS_ROUNDS` | `10s` / `10` | Длительность прогона набора ws / эхо-циклов на соединение |
| `BOUNDARY_DURATION` / `BOUNDARY_LADDER` / `BOUNDARY_ERR_PCT` | `30s` / `5000 15000 30000` / `1` | длительность разгона на ступень / потолки VU / порог доли ошибок в процентах для набора boundary |
| `BOUNDARY_MAX_VUS` | не задан | Замена `BOUNDARY_LADDER` одной ступенью (устаревшее написание) |
| `BOUNDARY_JMETER_HEAP` | `-Xms512m -Xmx4g` | heap JMeter на высоких ступенях boundary |
| `DB_DURATION` / `DB_WARM_QUERIES` / `DB_TX_CYCLES` | `10s` / `10` / `5` | длительность сценария db / запросов на тёплую итерацию / циклов транзакций на итерацию |
| `BENCH_PG_DSN` | `postgres://postgres:perfscale@127.0.0.1:5432/postgres` | DSN PostgreSQL для набора db |
| `BENCH_PG_JDBC_JAR` | определяется из `lib/` JMeter | jar JDBC-драйвера PostgreSQL для строки JMeter db |
| `K6_SQL_BIN` | `target/xk6-sql/k6` | Кастомный k6 с расширением xk6-sql для строки k6 набора db (собирается bench-workflow) |
| `PORT` / `TLS_PORT` | `18999` / `18998` | Порты для одноразовых целей serve |
| `OUTPUT` | `bench-report.md` | Путь к Markdown-отчёту |
| `RESULTS` | `bench-results.json` | Машиночитаемые результаты (вход для отслеживания регрессий) |
| `PERFSCALE_BIN` | `target/release/perfscale` | Тестируемый бинарник; собирается при отсутствии |

## Запуск в CI (канонический)

[Workflow `bench`](../.github/workflows/bench.yml) выполняется на
`ubuntu-latest` — фиксированный класс раннера, что устраняет разброс между
локальными машинами:

- **вручную**: GitHub → Actions → `bench` → *Run workflow* (параметры: `vus`,
  `duration`, `runs`, `suites`)
- **еженедельно**: по расписанию, понедельник 04:00 UTC, как проверка дрейфа
  производительности

Сводка задачи содержит таблицу окружения (ОС/CPU/потоки/RAM/swap) и таблицу
ПО (версии perfscale/k6/locust/jmeter/java/hyperfine) перед результатами.
Артефакт `bench-report` (хранится 90 дней) содержит markdown-отчёт и
`bench-results.json`.

### Отслеживание регрессий

Каждый CI-прогон скачивает `bench-results.json` предыдущего успешного прогона
и добавляет в сводку таблицу дельт (`scripts/bench_compare.py`): RPS,
задержка, RSS, накладные расходы на запуск и средние criterion, с пометкой
изменений свыше ±15%. Раннеры — общее оборудование, поэтому регрессии
**предупреждают**, а не роняют задачу — воспринимайте пометку как «посмотри
сюда», подтверждая повторным прогоном.

## Как читать числа

- `overhead`: относительное время выполнения около 1.00 = обёртка бесплатна
  на этой длительности. Реальные различия движков — в `throughput`.
- `throughput`: сравнивайте RPS и перцентили; `CPU per req` нормализует
  стоимость CPU по фактически выполненной работе (движок, потребляющий в 2
  раза больше CPU при в 10 раз большем RPS, *эффективнее*, а не меньше).
- `startup`: `vs native` — собственная стоимость обёртки; `vs ideal` включает
  также старт самого движка.
- Никогда не сравнивайте между машинами или CI-прогонами — только внутри
  одного отчёта (таблица дельт сравнивает между прогонами *на одном классе
  раннеров*, а это наиболее близкое к корректному сравнение).

### Как читать `IO ops` (`in` / `out`)

`N in / M out` — это счётчик файловых операций из прогона под
`/usr/bin/time`:

- **`in`** — операции чтения: блоки, прочитанные *с* файловой системы
  (загрузка скриптов/конфигов, подкачка бинарников). `0 in` — норма для
  тёплого прогона: всё уже в страничном кэше. Холодный первый прогон
  показывает ненулевое `in` (например, k6 подкачивает свой бинарник).
- **`out`** — операции записи: блоки, записанные *на* файловую систему
  (временные скрипты, статистика locust `--csv`, логи).

Единицы IO ops различаются между ОС (GNU time считает блоки ФС на Linux; BSD
time считает блочные операции на macOS), поэтому одно и то же число **не**
означает одинаковый объём байт в разных системах — сравнивайте только внутри
одного отчёта.
