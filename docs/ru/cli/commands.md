# Команды CLI

```text
perfscale run          Run a load test with k6, locust, JMeter, or the native step engine
perfscale serve        Start a local dev server that receives metrics from `run --report`
perfscale lint         Validate test/config YAML files without running them
perfscale install      Fetch remote libraries and pin them in perfscale.lock
perfscale burn         Build a standalone binary with WASM libraries embedded
perfscale schema       Print the JSON Schema for test or config YAML files
perfscale man          Print the bundled man page (or install it for `man perfscale`)
perfscale self-update  Update perfscale to the latest release for this platform
```

## `perfscale run`

Требуется ровно один флаг движка: `--k6`, `--locust`, `--jmeter` или `-f`.

| Флаг | Значение | Описание |
|---|---|---|
| `--k6 <FILE>` | `.js`-скрипт | Запуск через бинарник `k6` из `PATH` |
| `--locust <FILE>` | locustfile | Запуск через бинарник `locust` из `PATH`, в headless-режиме |
| `--jmeter <FILE>` | `.jmx` тест-план | Запуск через бинарник `jmeter` из `PATH`, без GUI (`jmeter -n -t`). План сам определяет профиль нагрузки — конфигурация perfscale не применяется |
| `-f, --file <FILE>` | `test.yaml` | Запуск со встроенным нативным движком (требует `-c`) |
| `-c, --config <FILE>` | `config.yaml` | Конфигурация нагрузки: `vus`, `duration`, опционально `report.url`. Обязателен с `-f`, для `--locust` — опциональная подсказка о нагрузке, для `--k6` и `--jmeter` игнорируется |
| `--host <URL>` | базовый URL | Целевой хост для `--locust` (аналог `--host` у locust) |
| `--report <URL>` | базовый URL | Отправить POST-запросом итоговую сводку на экземпляр `perfscale serve` после прогона; переопределяет `report.url` из конфигурационного файла |
| `-q, --quiet` | — | Подавить вывод по каждому запросу; ошибки и итоговая сводка метрик по-прежнему печатаются. Нативный движок отбрасывает эти строки прямо у источника, что заодно убирает накладные расходы на их форматирование и ввод-вывод под высокой нагрузкой |
| `--summary-export <FILE>` | путь, повторяемый | После прогона записать в этот файл разобранную сводку метрик (запросы, RPS, перцентили задержки, доля ошибок) вместе с метаданными прогона (движок, VU, длительность, метка времени, версия perfscale). Повторите флаг, чтобы записать несколько экспортов за один прогон. Расширение `.md`/`.json` выбирает формат для каждого файла (по умолчанию JSON) |
| `--summary-format <json\|md>` | вместе с `--summary-export` | Формат для файлов экспорта без распознанного расширения. `md` рендерит таблицу для сводок заданий CI: `--summary-export "$GITHUB_STEP_SUMMARY" --summary-format md` |
| `--allow-remote-import` | — | Разрешить `import:` в документах `-f`/`-c` загружаться по сети (http(s) URL, git-репозитории). По умолчанию запрещено (fail-closed) — документ не может сам себе выдать доступ к сети. См. [импорты](../core/imports.md) |
| `--refresh-imports` | — | Повторно загрузить кэшированные git-импорты по тегу/ветке вместо доверия кэшу (импорты по SHA коммита неизменяемы и никогда не перезагружаются) |

### Семантика кодов выхода

- `0` — прогон завершён, **даже если запросы или проверки завершались неудачей**. Провалившиеся
  проверки — это обратная связь нагрузочного теста (видна в `http_req_failed` и в stderr),
  а не ошибка CLI — как поведение k6 по умолчанию без порогов (thresholds). Это
  также касается движков, которые выходят с ненулевым кодом при провалившихся *запросах* (k6 с
  thresholds, locust), если они выдали сводку результатов.
- `1` — прогон не удалось выполнить: файл не найден, некорректный YAML, бинарник
  движка не найден или движок упал до выдачи каких-либо результатов (ненулевой
  выход с нулевыми метриками — ошибка в скрипте или сломанная установка, а не обратная
  связь теста): `error: engine exited with code 1 before producing any results`.
  Кроме того: нативный прогон, у которого gate
  [`std/thresholds@v1`](../core/actions.md#stdthresholdsv1)
  дал результат `fail` (`error: thresholds failed: …`) — gates позволяют CI
  превращать нарушения SLO в провалившуюся сборку, как thresholds в k6.
- `2` — некорректные аргументы командной строки.

### Потоки вывода

- **stdout** — вывод движка и итоговая сводка метрик (машиночитаемый формат)
- **stderr** — ошибки, провалившиеся проверки и маркеры прогресса `[system]`. Прогоны,
  выполняемые через машинного агента, завершаются финальным маркером
  `[sys] __perfscale_exit__=<code>`, несущим код выхода движка —
  см. [Раннеры → маркер выхода](../core/runners.md#exit-marker-on-agent-streams)

### Экспорт сводки

`--summary-export` записывает самоописательный файл результатов после прогона:

```json
{
  "meta": {
    "perfscale_version": "0.2.0",
    "engine": "native",
    "vus": 10,
    "duration": "30s",
    "timestamp": "2026-07-08T11:11:17Z"
  },
  "summary": {
    "avg_ms": 0.09, "med_ms": 0.08, "p90_ms": 0.15, "p95_ms": 0.17,
    "p99_ms": 0.27, "min_ms": 0.02, "max_ms": 2.86,
    "error_rate": 0.0, "total_requests": 20872, "requests_per_sec": 20866.54
  }
}
```

`vus`/`duration` равны `null` для прогонов `--k6` и `--jmeter` (профиль нагрузки
задан в скрипте/плане). То же верно для нативных прогонов с профилем `stages:`/`arrival:` —
фиксированного числа VU нет, поэтому `vus` равен `null`, а `duration` — суммарная
длительность шагов (например, `"90s"`); строка `vus` в сводке в этом случае показывает
наблюдаемый минимум/максимум параллелизма. `summary` равен `null`, если прогон не дал
HTTP-метрик. Если в конфигурации был gate
[`std/thresholds@v1`](../core/actions.md#stdthresholdsv1),
в экспорте появляется поле `thresholds` с результатом gate:

```json
{
  "thresholds": {
    "status": "fail",
    "message": "db_query_failed rate=1 ≥ 0.05; checkout SLO",
    "violations": [{ "metric": "db_query_failed", "expr": "rate<0.05", "actual": 1.0 }]
  }
}
```

`status` равен `pass`, когда все выражения выполнились, иначе — `severity`
gate (`fail`/`warn`/`info`). Статус `fail` также заставляет `perfscale run` завершиться
с ненулевым кодом, так что CI падает на самом gate. С
`--summary-format md` те же данные рендерятся как таблица Markdown — если направить её в
`$GITHUB_STEP_SUMMARY`, она попадёт прямо в сводку задания GitHub Actions.
Неудачная запись экспорта — ошибка CLI (код выхода 1), даже если сам прогон
завершился успешно: CI не должен молча продолжаться без запрошенного артефакта.

### Ошибки доступности движков

```text
error: k6 not found in PATH — install from https://k6.io/docs/get-started/installation/
error: locust not found in PATH — install with `pip install locust` (...)
error: jmeter not found in PATH — install from https://jmeter.apache.org/download_jmeter.cgi (...)
```

Прогоны JMeter не выдают перцентилей задержки: после прогона финальная
консольная строка `summary =` jmeter преобразуется в совместимый с k6 блок сводки
только с `avg`/`min`/`max`. Интеграции `std/thresholds@v1` для
`--jmeter` нет — код выхода процесса jmeter и есть gate.

## `perfscale serve`

| Флаг | По умолчанию | Описание |
|---|---|---|
| `--port <PORT>` | `7999` | Порт для прослушивания; `0` выбирает свободный порт (печатается при запуске) |
| `--tls` | выкл. | Обслуживать HTTPS с самоподписанным сертификатом, сгенерированным при запуске, — локальная TLS-цель для нагрузочных тестов. Клиенты должны пропускать проверку сертификата (`insecure: true` в `std/http@v1`, `insecureSkipTLSVerify` у k6, `verify=False` у locust) |
| `--no-ui` | выкл. | Не обслуживать встроенный дашборд на `/`; API приёма метрик продолжает работать |

Эндпоинты:

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/` | Встроенный дашборд (отсутствует с `--no-ui`): живые временные ряды снапшотов во время прогона и последние сводки прогонов. Самодостаточный — без CDN и шага сборки; опрашивает `/api/v1/state` |
| `GET` | `/health` | Возвращает `ok` |
| `POST` | `/api/v1/metrics` | Принимает итоговую сводку `{"lines": ["...", ...]}` или снапшот во время прогона `{"samples": [...], "seq": N}` (`report.during_run`), печатает его и хранит в памяти для дашборда |
| `GET` | `/api/v1/state` | Недавние пакеты снапшотов и последние сводки прогонов в JSON — то, что опрашивает дашборд. Хранится только в памяти: последние 2000 пакетов снапшотов и 20 сводок |
| `GET` | `/ws` | WebSocket-эхо — каждое текстовое (и бинарное) сообщение возвращается дословно. Петлевая (loopback) цель для WebSocket-нагрузочных тестов и бенчмарк-набора `ws` |

Это заменитель для разработки, а не control-plane: ни персистентности, ни аутентификации,
ни агрегации между прогонами. Его может заменить всё, что умеет работать с этими эндпоинтами.

## Бенчмаркинг

В perfscale нет подкоманды `bench` — сравнения движков запускаются через
[`scripts/bench.sh`](../../scripts/bench.sh), скрипт на базе
[hyperfine](https://github.com/sharkdp/hyperfine). Методология и использование описаны в разделе [Бенчмарки](../benchmarks.md).

## `perfscale lint`

Проверяет YAML-файлы по тем же схемам, что использует `run`, — плюс проверки,
которые схема выразить не может, — ничего не выполняя. Предназначен для редакторов, CI
gate'ов и pre-commit-хуков.

```sh
perfscale lint test.yaml config.yaml
perfscale lint --schema config load.yaml
```

| Флаг | По умолчанию | Описание |
|---|---|---|
| `FILE...` | обязательный | Один или несколько YAML-файлов |
| `--schema <auto\|test\|config>` | `auto` | `auto` определяет тип по файлу: ключ верхнего уровня `steps:` означает определение теста, всё остальное — конфигурация |
| `--offline` | выкл. | Пропустить сетевой проход (интроспекция GraphQL) — проверять только офлайн |
| `--allow-remote-import` | выкл. | Разрешить `import:` в проверяемых документах загружаться по сети, чтобы можно было валидировать объединённый результат |
| `--refresh-imports` | выкл. | Повторно загрузить кэшированные git-импорты по тегу/ветке вместо доверия кэшу |

Что проверяется:

0. **Импорты** — документы с ключом `import:` сначала разрешаются и объединяются,
   так что валидация видит то, что реально будет выполняться. Проблемы разрешения
   (отсутствующая база, цикл, удалённый импорт без `--allow-remote-import`)
   сообщаются как находки по адресу `/import`
1. **Синтаксис YAML** — ошибки разбора с подсказкой про отступы/кавычки
2. **JSON Schema** — обязательные поля, типы (та же валидация, что выполняет `run`)
3. **Неизвестные/опечаточные поля** — с подсказками «возможно, вы имели в виду» (`chek` → `check`),
   на каждом уровне: поля шагов, параметры `with:` каждого действия, ключи `check:`,
   поля конфигурации, поля `report:`
4. **Неизвестные идентификаторы действий** — `std/htp@v1` → `did you mean 'std/http@v1'?`
5. **GraphQL-документы** — запросы `std/graphql@v1` разбираются (синтаксические ошибки
   указывают на `/steps/N/with/query`) и, когда эндпоинт доступен,
   валидируются по его интроспектированной схеме. Шаги со `schema_file` валидируются
   по локальному SDL, а недоступные эндпоинты дают информационную заметку, но никогда не провал. `--offline` пропускает сетевой проход

Каждая находка показывает *где* (`/steps/0/with`), *что* не так и *что использовать
вместо*, а вывод завершается ссылкой на
[справочник по YAML](../yaml-reference.md).

Код выхода: `0`, если все файлы валидны, иначе `1` — безопасно использовать как CI
gate:

```yaml
- run: perfscale lint tests/*.yaml
```

## `perfscale install`

Загружает удалённые библиотеки генераторов значений (RFC 005), объявленные в
`libraries:`, и фиксирует их для офлайн-прогонов.

```sh
perfscale install test.yaml config.yaml
perfscale install test.yaml --refresh   # re-resolve git refs
```

Каждый `use:`, являющийся URL `https://…` или ссылкой
`git+<repo>@<ref>#<path>`, загружается один раз — включая объявления,
найденные через цепочки `import:` — проверяется по дайджесту на соответствие его пину `sha256:`
(только объявленные пины; см. ниже), сохраняется в
контентно-адресуемом кэше (`<cache>/libraries/<sha256>.wasm`) и записывается
в TOML-файл `perfscale.lock` рядом с объявляющим файлом (git-ссылки фиксируются на
разрешённый коммит). Закоммитьте lockfile: `run` и `lint` разрешают удалённые
библиотеки через lock + кэш **полностью офлайн**, а отсутствующий пин или
артефакт кэша — жёсткая ошибка с указанием запустить `perfscale install`.

`sha256:` опционален для источников `https://…` (как и в агенте
perfscaled): без него дайджест загруженного артефакта вычисляется, фиксируется в
lockfile и печатается с предупреждением, советующим добавить пин в
YAML. При наличии пина несовпадение — жёсткая ошибка с указанием обоих дайджестов.

Код выхода: `0`, если все удалённые библиотеки установлены (или уже зафиксированы),
`1` при ошибках загрузки/проверки (несовпадение sha256 называет оба дайджеста).

`install` также *встраивает* (burn) каждую WASM-библиотеку — удалённую и локальную — в AOT-
кэш (`<cache>/libraries/<sha256>.cwasm`), так что `run`/`lint` десериализуют
предварительно скомпилированный артефакт вместо компиляции на каждый прогон. Эта операция
необязательна: библиотека, которую не удалось предкомпилировать, понижается до предупреждения
и компилируется во время выполнения.

## `perfscale burn`

Собирает автономный бинарник со встроенными WASM-библиотеками из документов:

```sh
perfscale burn -f test.yaml -c config.yaml -o ./perfscale+libs
```

| Флаг | По умолчанию | Описание |
|---|---|---|
| `-f, --file <FILE>` | обязательный, повторяемый | YAML-документ(ы) теста, чьи `libraries:` нужно встроить |
| `-c, --config <FILE>` | — | Опциональная YAML-конфигурация, чьи `libraries:` также нужно встроить |
| `-o, --output <FILE>` | обязательный | Путь выходного производного бинарника |

Результат — побайтовая копия запущенного бинарника perfscale плюс
AOT-предкомпилированные (`.cwasm`) артефакты всех объявленных WASM-библиотек,
дописанные за маркером-окончанием `PFSEMBED`. Производный бинарник разрешает эти
библиотеки из самого себя — ни файлы `.wasm`, ни кэш, ни `perfscale.lock`
на машине запуска не нужны — что делает его однофайловым дистрибутивом для
генераторов нагрузки и контейнеров (см.
[Запуск perfscale в Docker](../core/docker.md#wasm-libraries)).

Удалённые ссылки должны быть сначала установлены (`perfscale install`) — `burn` разрешает
их через lock + кэш офлайн, как `run`. Встроенные `@std` — это нативный
код, они пропускаются автоматически. Артефакты burn привязаны к сборке,
которая их произвела (версия wasmtime, target triple, конфигурация движка):
повторно запускайте `perfscale burn` после обновления perfscale. Burn устраняет
компиляцию на прогон, но не накладные расходы на вызов — стоимость вызова библиотеки не меняется.

Код выхода: `0` при успехе, `1`, если документ не загружается, WASM-библиотеки
не объявлены или библиотека не компилируется как компонент.

## `perfscale schema`

Печатает JSON Schema, по которой perfscale валидирует YAML-файлы, — точно те
схемы, что используют `lint` и `run`, в виде форматированного JSON на stdout.

```sh
perfscale schema test     # schema for test definitions (steps)
perfscale schema config   # schema for run configs
```

Предназначен для всего, что программно создаёт YAML для perfscale:

- **Автодополнение в редакторе** — направьте ваш языковой сервер YAML на этот вывод
- **Инструментарий агентов** — [MCP-сервер perfscale](../mcp.md) вызывает эту команду, чтобы
  дать моделям контракт авторинга

Код выхода: `0` при успехе.

## `perfscale man`

Печатает встроенную man-страницу — полный справочник CLI, вкомпилированный в
бинарник при сборке. Это путь для **Windows**, где нет `man(1)`:

```sh
perfscale man          # plain-text manual on stdout
perfscale man --raw    # the roff source instead
```

В Unix установите страницу один раз, чтобы работал `man perfscale`:

```sh
perfscale man --install                                # → ~/.local/share/man/man1
perfscale man --install --dir /usr/local/share/man/man1  # system-wide
```

`--install` записывает `perfscale.1` в выбранную директорию и обновляет
man-индекс, если доступен `mandb`. Если после этого `man perfscale` не находит страницу,
добавьте родительскую директорию в `MANPATH`:

```sh
export MANPATH="$HOME/.local/share/man:$MANPATH"
```

Глобальная установка через npm (`npm install -g @perfscale/exe`) связывает man-страницу
автоматически — поле `man` в npm помещает её в
`<prefix>/share/man/man1`.

Код выхода: `0` при успехе, `1`, если `--install` не может записать в директорию.

## `perfscale self-update`

Заменяет запущенный бинарник на последний
[релиз GitHub](https://github.com/Perfscale/perfscale/releases) для этой
платформы. sha256 загрузки проверяется по `sha256sums.txt` релиза
до замены, а сама замена атомарна (файл сначала подготавливается рядом
с исполняемым, затем переименовывается) — неудачное обновление никогда не оставляет
после себя сломанный бинарник.

```sh
perfscale self-update              # update to the latest release
perfscale self-update --check      # only check; exit 10 = update available
perfscale self-update --force      # reinstall even if already up to date
```

| Флаг | Описание |
|---|---|
| `--check` | Сообщить, есть ли обновление, не устанавливая его. Коды выхода: `0` — актуально, `10` — обновление доступно; удобно для скриптов в cron/CI |
| `--force` | Переустановить последний релиз, даже если версии совпадают |

### Установки через npm

Когда perfscale установлен через `npm install -g @perfscale/exe`, бинарник
принадлежит npm — замена его на месте оставила бы метаданные пакета npm,
утверждающие про старую версию. `self-update` обнаруживает это (исполняемый файл находится
в `node_modules/@perfscale/`) и отказывается, предлагая правильную команду:

```sh
npm install -g @perfscale/exe@latest
```

`--check` по-прежнему работает, а пассивная подсказка ниже предлагает npm-команду
для npm-установок автоматически.

### Пассивная подсказка «доступно обновление»

Другие команды (`run`, `serve`, `lint`) печатают однострочную подсказку в stderr,
когда известен более новый релиз:

```text
perfscale v0.2.0 is available (you have 0.1.0) — run `perfscale self-update`
```

Проверка намеренно ненавязчива: не более одного сетевого запроса за 24 часа
(кэшируется в пользовательской директории кэша), только в интерактивных терминалах (никогда в
логах CI или пайпах), никогда не задерживает команду более чем на ~2 с и молчит
офлайн.

| Переменная | Эффект |
|---|---|
| `PERFSCALE_NO_UPDATE_CHECK=1` | Полностью отключить пассивную проверку и подсказку |
| `PERFSCALE_UPDATE_API_BASE` | Переопределить хост API релизов (по умолчанию `https://api.github.com`) — для зеркал/прокси |
| `PERFSCALE_UPDATE_DOWNLOAD_BASE` | Переопределить хост загрузки артефактов (по умолчанию `https://github.com`) |

## Переменные окружения

| Имя | Описание |
|---|---|
| `RUST_LOG` | фильтр `tracing`, например `RUST_LOG=debug perfscale run ...` |
| `PERFSCALE_NO_UPDATE_CHECK` | `1` отключает подсказку о доступном обновлении |
| `PERFSCALE_CACHE_DIR` | Корень кэша для git-клонов `import:` и установленных библиотек (по умолчанию `~/.cache/perfscale`) |
