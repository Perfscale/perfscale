# Метрики

Нативный движок записывает каждый шаг, похожий на запрос, в HDR-гистограмму
фиксированного размера и сворачивает пользовательские счётчики/гистограммы из
выводов действий в те же агрегаты запуска. Два выхода: машиночитаемая строка
`[stats]` каждые 5 секунд во время запуска и k6-совместимая сводка в конце.

## Метрики запросов (`http_req_*`)

Действия, выполняющие измеряемый по времени запрос, возвращают `HttpSample`
(`duration_ms`, `status`, `failed`). Длительности записываются в
**микросекундах** — вызовы через loopback короче миллисекунды остаются различимыми.

| Действие | Что попадает в `http_req_duration` | Что считается ошибкой |
|---|---|---|
| `std/http@v1` | Каждый запрос | Статус ≥ 400, транспортная ошибка, таймаут (логируется как `→ TIMEOUT after …ms`; `status` указывается как 0) |
| `std/tcp@v1` | Connect + обмен send/read | Ошибка соединения, таймаут, несовпадение с `expect` |
| `std/udp@v1` | Отправка (+ опциональное ожидание ответа) | Таймаут, несовпадение с `expect` |
| `std/ws@v1` | Вся one-shot-сессия целиком (один сэмпл) | Ошибка рукопожатия/транспорта, правило `until_*`, не выполненное вовремя |
| `std/ws-connect@v1` | Только рукопожатие | Ошибка рукопожатия (`connected: false`) |

Намеренно **не** попадают в `http_req_duration` — шаг, чья длительность
ничего не говорит о задержке цели, отравил бы общие процентили:

| Действие | Почему |
|---|---|
| `std/ws-recv@v1` | То, сколько сервер ждёт перед отправкой, — не задержка цели |
| `std/ws-ping@v1` | Транспортный RTT; вместо этого ограничивайте его через `check: { duration_ms_lt: … }` |
| `std/ws-send@v1`, `std/ws-close@v1` | Нет осмысленной задержки запроса |
| `std/grpc*@v1` (всё семейство) | У gRPC свои гистограммы (`grpc_req_duration`, `grpc_msg_rtt`); время жизни стримов выходит за пределы шагов пользователя, поэтому стримы не попадают даже в них |
| `std/db-*@v1` (всё семейство) | У DB-шагов свои гистограммы (`db_connect_duration`, `db_query_duration`) и счётчики (`db_rows`, `db_errors`) |
| `std/child_process@v1`, `std/kill_process@v1` | Жизненный цикл процесса, а не запросы |
| `std/check@v1`, `std/sleep@v1`, `std/log@v1`, `std/file-*@v1` | Нет сетевого ввода-вывода |

Обратите внимание на асимметрию: ошибки gRPC-утверждений попадают в
`grpc_req_failed` (пользовательский счётчик, управляемый `expect_status`),
**а не** в `http_req_failed`.

## Итоговая сводка

Выводится в конце каждого запуска, k6-совместимая, чтобы нижестоящие парсеры
(дашборды, `perfscale serve`) обрабатывали все движки единообразно:

```text
vus....................: 10 min=1 max=10
iterations..............: 4521 150.23/s
http_req_duration......: avg=0.42ms p(50)=0.31ms p(90)=0.88ms p(95)=1.02ms p(99)=1.90ms min=0.09ms max=3.10ms
http_req_failed........: 0.00%
http_reqs..............: 4521 150.23/s
```

- `vus` / `iterations` (+ скорость в секунду) выводятся всегда, даже для
  запусков, состоящих только из sleep.
- `dropped_iterations` всегда выводится для запусков с arrival rate — 0, если
  пул справлялся, — чтобы пороговые проверки (`dropped_iterations: ["count==0"]`)
  разрешались, а не падали с ошибкой на неизвестной метрике.
- Блок `http_req_*` появляется только когда записан хотя бы один сэмпл.
- Процентили берутся из HDR-гистограммы фиксированного размера (диапазон 1 мкс –
  1 ч, два значащих разряда → ошибка квантиля ≤1%) — потребление памяти не
  растёт независимо от длительности soak-теста ценой погрешности, невидимой
  на выводимой точности.

## Живые строки `[stats]`

Каждые 5 секунд, пока работают VU, выводится одна машиночитаемая строка:

```text
[stats] ts=1720000000000 rps=246.80 err_pct=0.00 p50=1.20 p90=3.40 p95=4.10 p99=8.20 reqs=1234 iters=456
```

- `ts` — миллисекунды unix-эпохи; `rps` — запросы за только что завершившееся
  5-секундное окно; `err_pct` — кумулятивный процент ошибок; `p50`…`p99` —
  кумулятивные процентили в мс (гистограмма никогда не сбрасывается, поэтому
  они сходятся, а не дрожат); `reqs` — суммарное число запросов; `iters` —
  суммарное число итераций.
- Пока запросов не было, процентили опускаются:
  `[stats] ts=… rps=0.00 reqs=0 iters=3`.
- Эти строки существуют для потоковых потребителей (controlplane разбирает их
  из потока логов); о поведении консоли см. [`--quiet`](#quiet).

## Пользовательские метрики (`value.metrics`)

Любое действие может прикрепить зарезервированный объект `metrics` к выводу
своего шага; раннер сворачивает его в агрегаты запуска:

- **Число** становится счётчиком, суммируется по всем VU и итерациям,
  выводится как `<name>: <total> <rate>/s`.
- **Массив чисел** становится сэмплами HDR-гистограммы (миллисекунды),
  выводится как
  `<name>: avg=…ms p(50)=… p(90)=… p(95)=… p(99)=… min=… max=… count=N`.

Встроенные эмиттеры:

| Имя | Тип | Кем эмитируется | Значение |
|---|---|---|---|
| `ws_msgs_sent` | counter | `std/ws@v1`, `std/ws-send@v1` | Отправлено WS-сообщений |
| `ws_msgs_received` | counter | `std/ws@v1`, `std/ws-recv@v1` | Прочитано WS-сообщений |
| `ws_msg_rtt` | histogram | `std/ws@v1`, `std/ws-recv@v1` | Отправка → первый подходящий ответ (RTT на уровне приложения) |
| `pubsub_msgs_published` | counter | `std/pubsub@v1` | Сообщений принято транспортом |
| `pubsub_msgs_received` | counter | `std/pubsub@v1` (с `subscribe`) | Сообщений, учтённых в `subscribe.count` |
| `pubsub_e2e_ms` | histogram | `std/pubsub@v1` (с `subscribe`) | Начало фазы публикации → сообщение обработано, один сэмпл на каждое совпавшее сообщение |
| `shared_variable_wait_ms` | histogram | `std/get_shared_variable@v1` (с `wait_for`) | Время блокировки в `wait_for` до выполнения условия, один сэмпл на каждое ожидающее чтение |
| `llm_ttft_ms` | histogram | `std/llm@v1` (стриминг) | Начало запроса → первый чанк контента (время до первого токена) |
| `llm_tokens_per_sec` | histogram | `std/llm@v1` | Токены завершения / время генерации (после первого токена при стриминге) |
| `llm_prompt_tokens` | counter | `std/llm@v1` | Токены промпта по данным сервера |
| `llm_completion_tokens` | counter | `std/llm@v1` | Токены завершения по данным сервера |
| `llm_chunks` | counter | `std/llm@v1` (стриминг) | Получено SSE-чанков |
| `grpc_req_duration` | histogram | `std/grpc@v1`, `std/grpc-call@v1` | Задержка унарного вызова |
| `graphql_req_duration` | histogram | `std/graphql@v1` | Полный цикл GraphQL-операции |
| `graphql_errors` | counter | `std/graphql@v1` | Ошибки уровня GraphQL, включая ответы с частичными данными, которые проходят шаг |
| `graphql_op_<operationName>_duration` | histogram | `std/graphql@v1` | Задержка по операциям, только для именованных операций (ограниченная кардинальность) |
| `grpc_msg_rtt` | histogram | `std/grpc-call@v1`, `std/grpc-stream-recv@v1` | Отправка → RTT подходящего ответа |
| `grpc_msgs_sent` | counter | `std/grpc-call@v1`, `std/grpc-stream-send@v1` | Отправлено gRPC-сообщений |
| `grpc_msgs_received` | counter | `std/grpc-call@v1`, `std/grpc-stream-recv@v1`, `std/grpc-stream-close@v1` | Прочитано gRPC-сообщений |
| `grpc_req_failed` | counter | `std/grpc-call@v1`, `std/grpc-stream-close@v1` | Вызовы, не прошедшие `expect_status` |
| `db_connect_duration` | histogram | `std/db-connect@v1` (успех) | Задержка соединения + настройки пула |
| `db_query_duration` | histogram | `std/db-query@v1`, `std/db-tx-*@v1` | Задержка запроса; в режиме соединения на каждый запрос включает новый connect |
| `db_rows` | counter | `std/db-query@v1` | Возвращённые строки, либо затронутые строки, если выражение не вернуло ни одной |
| `db_errors` | counter | `std/db-*@v1` (ошибка) | Неудачные DB-шаги, всего. Успешные DB-шаги эмитируют `db_errors: 0`, поэтому счётчик существует (равный 0) даже на полностью здоровых запусках — проверки вида `db_errors: ["count==0"]` работают в обоих случаях |
| `db_errors_connection` / `_constraint` / `_deadlock` / `_timeout` / `_other` | counter | `std/db-*@v1` (ошибка) | То же, разбитое по классам (SQLSTATE / errno / код результата SQLite) |

Нижестоящие действия используют тот же канал — например, проприетарное
FIX-действие эмитирует `fix_messages_sent`.

## Метрики доли ошибок (`<family>_failed`)

Помимо полезной нагрузки `metrics`, раннер универсально вычисляет сэмплы
ошибок по вызовам: для каждой гистограммной (массивной) метрики, которую
эмитирует вызов, он записывает один сэмпл 0/1 — 1, если вызов шага завершился
ошибкой, 0 при успехе — под именем семейства метрики с заменой хвоста
`_duration`/`_rtt` на `_failed`:

| Метрика длительности | Производная метрика ошибок |
|---|---|
| `http_req_duration` | `http_req_failed` (нативная для HTTP-пути) |
| `db_query_duration` | `db_query_failed` |
| `db_connect_duration` | `db_connect_failed` |
| `grpc_req_duration` | `grpc_req_failed` |
| `graphql_req_duration` | `graphql_req_failed` |
| `ws_msg_rtt` | `ws_msg_failed` |
| `pubsub_e2e_ms` | `pubsub_e2e_ms_failed` |
| `llm_ttft_ms` | `llm_ttft_ms_failed` |
| `llm_tokens_per_sec` | `llm_tokens_per_sec_failed` |

Они выводятся как `<name>: <pct>%` (в форме k6 `http_req_failed`). Поскольку
один сэмпл записывается **на вызов** (а не на сэмпл длительности),
`failed/total` по ним — это в точности доля ошибок семейства шагов — именно
её оценивает `std/thresholds@v1` с `rate`, например
`db_query_failed: ["rate<0.05"]`. Учтите: неудачный шаг, не эмитировавший
сэмпл длительности (например, `db-connect`, который так и не подключился),
также не записывает сэмпл, поэтому доля семейства покрывает только
завершённые вызовы.

Когда у семейства уже есть одноимённый счётчик (gRPC-действия эмитируют
счётчик `grpc_req_failed` для промахов `expect_status`), rate-метрика
затеняет его и в сводке, и при оценке порогов.

## Пороговые проверки запуска (`std/thresholds@v1`)

Шаг `std/thresholds@v1` (обычно в `after:`) оценивает выражения в стиле k6
по агрегатам запуска и выводит одну машиночитаемую строку после сводки метрик:

```text
thresholds: {"status":"fail","message":"db_query_failed rate=1 ≥ 0.05; checkout SLO","violations":[{"metric":"db_query_failed","expr":"rate<0.05","actual":1.0}]}
```

Агрегаты берутся из тех же HDR-гистограмм/счётчиков, что и текстовая сводка,
поэтому числа проверок совпадают с выводом сводки. Строка собирается в
вывод `perfscale run --summary-export` под ключом `thresholds`
(`{status, message, violations}`), а статус `fail` заставляет CLI завершиться
с ненулевым кодом. См. [actions.md](actions.md#stdthresholdsv1).

## Метрики GPU (`gpu:`)

При `gpu.enabled: true` в [конфигурации запуска](../yaml-reference.md#config--c-configyaml)
нативный движок сэмплирует каждый GPU на хосте — загрузку %, занято/всего
VRAM, температуру, потребляемую мощность — раз в `interval_ms` на протяжении
всей фазы VU (через `nvidia-smi` или эндпоинт dcgm-exporter). После сводки
метрик запуск выводит компактный блок по устройствам плюс одну машиночитаемую
строку `gpu: {...}` с полным временным рядом, которую `--summary-export`
вкладывает под ключом `gpu`:

```text
gpu: 1 device, 300 samples every 1000ms (nvidia-smi)
gpu0: util avg=64.3% max=100.0% vram max=41088/81559MiB temp max=71.0C power max=512.3W
gpu: {"source":"nvidia-smi","interval_ms":1000,"devices":[{"index":0,"samples":[…],…}]}
```

Сбор — наилучшее усилие: отсутствие GPU / необходимых утилит логируется одним
предупреждением, и запуск продолжается без метрик GPU. Метки времени сэмплов
делят общую шкалу epoch-мс со строками `[stats]`, поэтому нагрузка и
состояние GPU коррелируют напрямую — основной сценарий использования:
запуски [`std/llm@v1`](llm.md) против локальных серверов моделей. Полное
руководство: [gpu.md](gpu.md).

## `--quiet`

Два независимых слоя:

- **В источнике** (нативный движок): вывод об успешных итерациях — строки
  запросов, маркеры sleep, прошедшие проверки — даже не форматируется и не
  отправляется. Ошибки, провалившиеся проверки, строки `[stats]` и итоговая
  сводка всегда попадают в поток.
- **В принтере CLI**: при `--quiet` строки stdout выводятся только если это
  строки сводки в формате k6 (`vus`, `iterations`, `http_req_*`); stderr и
  системные строки выводятся всегда. Строки пользовательских метрик и `[stats]`
  остаются в потоке для потребителей логов, но скрываются из консоли.

## Пересылка сводки (`report`)

Укажите запуску экземпляр `perfscale serve`, и строки сводки будут пересланы
по завершении запуска:

```yaml
# config.yaml
report:
  url: http://localhost:7999
```

```sh
perfscale run -f test.yaml -c config.yaml --report http://localhost:7999
```

Флаг CLI имеет приоритет над блоком конфига. После запуска CLI отправляет POST
с собранными строками сводки (только в формате k6) как
`{"lines": […]}` на `<url>/api/v1/metrics` с таймаутом 5 с; проблемы доставки
логируются как `[report] …` в stderr и никогда не роняют сам запуск.

## Метрики во время запуска (`report.during_run`)

Тот же блок `report:` может также стримить метрики **пока запуск ещё идёт** —
кумулятивные снапшоты всех семейств метрик, пакетируемые и отправляемые POST
на тот же эндпоинт `<url>/api/v1/metrics`:

```yaml
report:
  url: http://localhost:7999
  during_run: true        # default false — only the end-of-run summary
  interval_ms: 5000       # snapshot/flush interval, min 100
  batch_size: 500         # flush a batch once it holds this many samples
  max_cpu_percent: 90     # CPU gate; 0 disables it
  max_pending: 24         # soft warn cap — batches are never dropped mid-run
```

Движок эмитирует один снапшот на `interval_ms` (независимо от 5-секундного
репортёра `[stats]`), а shipper их пакетирует: батч отправляется POST, как
только достигает `batch_size` сэмплов, а всё открытое сбрасывается на каждом
тике интервала. Каждое тело POST — `{samples, seq}` (плюс `taskId`, если
вызывающая сторона его задаёт), где `seq` — монотонно возрастающий номер
батча, переиспользуемый при повторах — получатели могут дедуплицировать
повторные доставки.

**Именование сэмплов** следует соглашениям Prometheus для summary/counter, с
конвертацией длительностей из миллисекунд движка в **секунды**:

| Метрика движка | Отправляемые сэмплы |
|---|---|
| histogram (`http_req_duration`, `db_query_duration`, …) | `<name>{quantile="0.5"/"0.9"/"0.95"/"0.99"}` (секунды), `<name>_count`, `<name>_sum` (секунды) |
| counter (`db_rows`, …) | `<name>_total` |
| доля ошибок (`http_req_failed`, …) | `<name>_total` (вызовы), `<name>_failed_total` (ошибки) |

Все значения **кумулятивные с начала запуска** — HDR-гистограммы и счётчики
никогда не сбрасываются во время запуска. Чтобы получить показатели за окно на
стороне потребителя, вычитайте соседние снапшоты: в стиле
`rate(x_count[window])` для пропускной способности, `Δ_sum / Δ_count` для
средней задержки за окно.

**Гейджи GPU стримятся тоже**, когда в запуске также включено
`gpu.enabled: true` (см. [метрики GPU](gpu.md)): каждый снапшот несёт сэмплы
GPU, снятые с момента предыдущего, как мгновенные гейджи с собственными
метками времени коллектора — отображайте их как есть, без дифференцирования:

| Отправляемый сэмпл | Метки | Единицы |
|---|---|---|
| `gpu_utilization_pct` | `gpu="<index>"` | проценты, 0–100 |
| `gpu_memory_used_mib` | `gpu="<index>"` | MiB |
| `gpu_memory_total_mib` | `gpu="<index>"` | MiB |
| `gpu_temperature_c` | `gpu="<index>"` | °C |
| `gpu_power_w` | `gpu="<index>"` | ватты |

Поля, которые источник сообщил как `N/A`, пропускаются (никогда не отправляются
как нули), а дополнительные поля pro-коллектора передаются под собственными
именами. Без `gpu.enabled` снапшоты вообще не содержат данных GPU.

**Защитные стратегии** (цикл VU всегда в приоритете; стриминг уступает первым):

- *CPU-гейт*: пока загрузка CPU хоста (из `/proc/stat`) равна или выше
  `max_cpu_percent`, ожидающие батчи удерживаются — без POST — а входящие
  снапшоты откладываются (ставятся в очередь, каждый десятый логирует
  предупреждение), затем сбрасываются в порядке поступления, когда гейт
  открывается. Вне Linux показаний CPU нет, поэтому гейт бездействует.
  `max_cpu_percent: 0` отключает его.
- *Неограниченный бэклог, мягкий предел*: запечатанные, но недоставленные
  батчи никогда не отбрасываются, пока запуск жив; превышение `max_pending`
  лишь логирует предупреждение с ограничением частоты. Доставка возобновляется
  по порядку, когда цель отвечает.
- *Повторы*: сетевые ошибки, 5xx и 429 повторяют тот же батч с
  экспоненциальной задержкой ×2 от 1 с, ограниченной 60 с. Любой другой 4xx
  считается ядом — батч отбрасывается и не повторяется.
- *Завершение*: когда запуск заканчивается, всё ещё ожидающее — включая
  снапшоты, отложенные CPU-гейтом, — сбрасывается с короткими ограниченными
  повторами (1/2/5/10 с), после чего shipper завершается. CLI ждёт этого
  финального дренажа (ограниченного), чтобы последний батч дошёл до выхода
  процесса.

Движок никогда не блокируется на стриминге: снапшоты идут через ограниченный
канал с `try_send`, и полный канал отбрасывает снапшот вместо обратного давления
на VU — единственное место, где точка может быть потеряна в середине запуска.
При отсутствующем или ложном `during_run` нет ни дополнительной задачи, ни
трафика канала вовсе.

Замечание по аутентификации: CLI отправляет без аутентификации (как и сводка
в конце запуска). Аутентифицированный путь — у агента: он запускает тот же
shipper с провайдером токенов Keycloak и `taskId` (также проставляемым как
метка `task_id` на каждом сэмпле).

**На платформе** (perfscale.su или self-hosted controlplane) поток оживляет
страницу запуска в реальном времени — квантили задержки, пропускная
способность, доля ошибок и кривые GPU рисуются по мере поступления сэмплов.
Агент подключает всё сам: `report.during_run: true` в конфигурации запуска —
единственное действие пользователя — он аутентифицирует поток своим машинным
токеном и помечает каждый сэмпл `task_id` и `machine_id`. Те же сэмплы питают
дашборд Metrics, Prometheus-совместимый query API (направьте Grafana на
`/api/v1/integrations/prometheus`) и Remote Write в ваш собственный
Prometheus/Mimir.
