# Нагрузочное тестирование с JMeter

perfscale запускает ваши **существующие тест-планы JMeter** (`.jmx`) в
headless-режиме и сводит результаты в тот же живой поток логов,
k6-совместимую сводку, гейты thresholds и отчёты, что и все остальные
движки. Ничего переписывать не нужно: возьмите уже имеющийся план, укажите
на него perfscale и получите живой вывод плюс машиночитаемые метрики,
которые можно сравнивать с прогонами k6, locust и нативного движка.

```sh
perfscale run --jmeter plan.jmx
```

## Предварительные требования

На машине, где выполняется тест, должна быть установлена JMeter — perfscale
оборачивает её, а не встраивает:

```sh
jmeter --version   # must be on PATH (requires a JRE)
```

Если бинарный файл не найден, запуск быстро завершается с ошибкой
`jmeter not found in PATH — install from https://jmeter.apache.org/download_jmeter.cgi (requires a JRE)`.
На агентах PerfScale Cloud dev-образ docker уже содержит JRE с
JMeter 5.6.3.

## Как проходит прогон

perfscale запускает план в non-GUI-режиме с приватным файлом результатов и
стримит всё в реальном времени:

```text
jmeter -n -t <plan.jmx> -j <temp>/jmeter.log -l <temp>/results.jtl -J…
```

- **JMeter полностью определяет форму нагрузки.** Thread groups, ramp-up,
  таймеры и пропускная способность — всё берётся из плана. Настройки
  `vus`, `duration`, `stages:`, `arrival:` из конфигурации perfscale не
  применяются (отклоняются с понятной ошибкой, а не молча игнорируются) —
  параметризуйте план [`-J`-свойствами](#параметризация-планов).
- **Детерминированные CSV-результаты.** Каждый прогон пишет сэмплы в
  приватный `results.jtl` в CSV-формате с фиксированным набором полей
  (`timeStamp`, `elapsed`, `label`, `success`, плюс
  `Latency`/`Connect`/`bytes`/`sentBytes`, когда план их выдаёт).
  Принудительные saveservice `-J`-свойства добавляются после ваших, поэтому
  пользовательское свойство не может сломать парсер. Оба временных файла
  удаляются по завершении прогона.
- **Живой вывод.** Собственные stdout/stderr JMeter стримятся во время
  прогона, так же как вывод k6 или locust.
- **Код выхода.** JMeter завершается с ненулевым кодом при ошибках плана
  или запуска; падения сэмплов внутри плана *не* меняют код выхода, если
  сам план на них не реагирует. perfscale добавляет два своих источника
  ошибок: файл результатов без достоверных сэмплов (невалидный заголовок
  или все строки повреждены) и нарушенный гейт
  `severity: fail` завершают прогон с кодом 1. В CI код выхода — это ваш
  гейт здоровья плана и SLO.

## Сводка из JTL

Файл результатов разбирается инкрементально (ограниченная память — сэмплы
складываются в HDR-гистограммы, а не в список) в то же хранилище метрик,
которое использует нативный движок. Сводка содержит полные перцентили:

```text
http_req_duration......: avg=4.12ms p(50)=3.00ms p(90)=6.00ms p(95)=8.00ms p(99)=21.00ms min=1.00ms max=72.00ms
http_req_failed........: 0.00%
http_reqs..............: 100 10.83/s
http_req_latency: avg=2.01ms p(50)=2.00ms … count=100
http_req_connect: avg=0.83ms p(50)=1.00ms … count=100
data_received: 102400 1109.00/s
data_sent: 51200 554.50/s
```

Метрики агрегируются **по каждому JMeter `label`**, а также глобально —
серии по label попадают в [документ `report@v1`](#отчёты) и в
потоковые снапшоты во время прогона. Число различных label ограничено (64
по умолчанию); сверх лимита сэмплы складываются в серию `__jmeter_other__`,
а строка `system` сообщает, сколько именно — кардинальность никогда не
растёт молча.

План с нулевым числом сэмплов (например, пустая thread group) откатывается
на трансляцию финальной консольной строки JMeter `summary =` (только
`avg`/`min`/`max`). Повреждённые строки пропускаются с предупреждением
`system`, пока достоверные сэмплы есть; файл с невалидным заголовком или
*только* повреждёнными строками — это падение прогона, а не молчаливый
пропуск.

## Параметризация планов

Передавайте свойства JMeter прямо из CLI — флаг повторяемый, значения могут
содержать `=`:

```sh
perfscale run --jmeter plan.jmx -Jvus=50 -Jloops=100 --jmeter-property host=staging.example.com
```

Ссылкаются на них в плане через property-функции со значениями по
умолчанию:

```xml
<stringProp name="ThreadGroup.num_threads">${__P(vus,5)}</stringProp>
<stringProp name="LoopController.loops">${__P(loops,20)}</stringProp>
<stringProp name="HTTPSampler.domain">${__P(host,127.0.0.1)}</stringProp>
```

Значения свойств никогда не печатаются в логи. Собственные настройки
saveservice раннера всегда побеждают пользовательские свойства.

## Thresholds и конфигурация

`perfscale run --jmeter plan.jmx -c config.yaml` применяет блок `report:` и
гейты `std/thresholds@v1` из `after:`:

```yaml
report:
  url: http://localhost:7999
  during_run: true            # стримить живые снапшоты из .jtl
  reporters:
    - use: std/report/junit@v1
      with: { path: junit.xml }
after:
  - use: std/thresholds@v1
    severity: fail            # fail (по умолчанию) | warn | info
    message: checkout SLO
    with:
      http_req_duration: ["p95<500", "p99<1500"]
      http_req_failed: ["rate<0.01"]
```

Гейты вычисляются по метрикам JTL (включая `http_req_latency`,
`http_req_connect`, `data_received`, `data_sent`) после прогона; нарушенный
гейт `severity: fail` завершает прогон ненулевым кодом — точно как в
нативном движке. `abort_on_fail` для JMeter **не поддерживается** (прогоном
управляет jmeter, поэтому гейт может сработать только после его завершения)
и отклоняется с понятной ошибкой — как и другие действия `after:`, шаги
`before:` и нативные блоки конфигурации.

## Отчёты

Финальные репортёры работают и для прогонов JMeter — раннер выпускает
канонический документ `report@v1`, построенный из реальных метрик, поэтому
JSON/JUnit/HTML-отчёты включают перцентили, серии по label и вердикты
thresholds:

```sh
perfscale run --jmeter plan.jmx --report json:report.json --report junit:junit.xml --label testid=smoke
```

С `report.during_run: true` (и `report.url` или потоковыми репортёрами)
кумулятивные снапшоты метрик стримятся из `.jtl` прямо во время прогона —
тот же конвейер, который питает нативный движок.

## Запуск на агенте (PerfScale Cloud)

Платформу обслуживает тот же раннер: тест типа JMeter хранит XML плана,
control plane отправляет его на агент, и агент выполняет его через
`POST /api/v1/run/jmeter` — стримя лог в реальном времени и помещая сводку
в тот же дашборд и тот же конвейер метрик, что и прогоны k6.

## Ограничения

- **Форма нагрузки живёт в плане.** `vus`/`duration`/`stages:`/`arrival:`
  из perfscale не применяются (отклоняются, а не игнорируются); используйте
  `-J`-свойства.
- **Нет `abort_on_fail`** — гейты вычисляются после завершения jmeter.
- Label со встроенными переводами строк могут смутить построчный живой
  тейлинг; финальный разбор всё равно учитывает их по правилам CSV-кавычек.

Сводное сравнение компромиссов по движкам см. в
[справочнике раннеров](runners.md#jmeter-runnerjmeter).
